## Six builder questions resolved at the design level

### Sequencing artifact

Create a proposed, separately reviewed sequencing amendment identifying the
released V2 base, original prerequisite contract hash, omitted M9 dependency
surfaces and every remaining M7/M8/Factual dependency. Keep the original
architecture acceptance immutable. The amendment cannot be represented by a
boolean in a caller request or by changing the old acceptance JSON. Until the
amendment is accepted, bootstrap returns `M10_PREREQUISITE_NOT_ACCEPTED` even if
the design is otherwise accepted. Never generate an acceptance record as part
of a resume checkpoint.

The existing factual contracts and Golden-A fixture are not evidence of a
durable correction/withdrawal/current-projection read service. A factual
required slot cannot be supplied by that fixture in an operational run. A
fictional content basis may omit a factual requirement only through the typed
profile's explicit applicability policy; it cannot bypass a declared required
slot or establish acceptance of a factual pilot.

### Profile, subject and package identities

A profile's complete body/policy digest does not contain a run, disposition or
package. The assessed subject binds the full host approved-master identity,
not just a display ID: scoped artifact key, master version, selected candidate,
content byte digest, approval reference, content basis and exact dependency
closure. Capture all source artifact heads required by currentness, including
the final's shot sources. Add an explicit frozen `MasterBinding` contract and
bind its digest in `AssessedSubject`; freeze its final field shape and digest
vector with the design candidate before A1, rather than guessing an ID encoding.
The original subject fields remain readable but cannot replace this binding.

B's package payload binds an already-existing master and member closure, with
no run/disposition/export digest inside it. Assessment then binds the package
subject; selection binds that assessment and decision; export binds selection.
This direction avoids a circular digest. B needs its own subject amendment and
cannot silently reuse A's artifact subject as a complete package assessment.

### Run and Human assessment lifecycle

An append-only observation belongs to one exact subject/profile/requirement/
slot and qualified assessor. Corrections create a new observation, not an edit.
Collecting observations are not a sealed QualityRun. Sealing recomputes the
closed union, ordered observation digest closure, ALL/N_OF_M count, required
independence groups, qualification, allowed applicability and named escalation.
Missing evidence, errors and disagreement that lacks its required escalation
block sealing a PASS-ready run. Repeating a request returns its exact receipt.

Publication of a profile and a run's becoming current have separate heads.
`HISTORICAL_ONLY` leaves applicable current readiness unchanged until normal
expiry; `REEVALUATE_CURRENT` invalidates affected current readiness. New active
run/profile/subject or revoked evidence stales the readiness projection without
rewriting historical observations. Disposition is a subsequent append-only
Human decision over the exact closure; it cannot finish missing assessments.
An aborted collection has no successful closure receipt.

### Shared M8 persistence and receipts

A creates only M10-owned foundation rows/receipts. Existing M8 command enums
and SQL constraints remain untouched. B may reuse accepted candidate revision
mechanics only through its reviewed schema amendment; M10 operations use M10
command receipts rather than unsupported M8 operation strings. Existing
`ExplorationPromotion` calls Production Authority and is not a package selector.
Receipt replay proves the historical result, never fresh export eligibility.

### Master closure and lock composition

Host references are `server.services.master_authority.serialized_artifacts`,
`verify_masters`, and `server.routers.gates._locked_to_heads`. Current host code
holds canonical master rows while validating the current projection. Reuse the
public service seam, not a router-private function or independent mutex.

The proposed A writer order is command guard -> complete sorted canonical
master-key set -> profile head -> active-run head -> disposition head. First
resolve a tentative closure outside the transaction; inside the host guard,
recompute it. If the required lock set changes, roll back and resolve again;
never acquire additional out-of-order rows or perform media/tool I/O while
holding locks. Receipt-first replay is followed by the command guard and a
second receipt lookup before any new work. Profile publication locks only its
command and profile head and must not invert the order by acquiring master rows.
A concurrent-writer inventory and PostgreSQL interleavings must validate this
order before freeze. It is a proposed order, not a concurrency proof.

### Packaging slot identity/cardinality

B will define one selected head per `(user_id, project_name, source_artifact_key,
cohort_id, product_surface)`; profile revision remains bound selection data,
not an extra independently selectable head. Historical revisions remain
append-only. Cross-cohort and cross-surface selections cannot replace each
other. Final normalized slot encoding and schema are B freeze work, with
collision, delimiter, case, cross-scope, migration and CAS fixtures. No A enum
or existing artifact key can stand in for that slot.
