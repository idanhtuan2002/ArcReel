# M8-C host high-water record and publication contract

Status: proposed wire/operation contract after the sponsor selected an operator-managed host directory. It is not an accepted signer ceremony, production mount, migration, startup mode or release gate. Reuse audit: `docs/research/2026-10-12-r2-m8c-host-custody-reuse-audit.md`.

## Existing byte and authority rules to preserve

`r2/contracts/governance_verifier_registry.py` already parses one canonical bounded registry and computes `sha256:` over its **raw file bytes**. `r2/contracts/grant_checkpoint.py` parses canonical signed envelope bytes, returns `checkpoint_digest` over its **canonical body bytes**, and keeps the raw envelope separately. `r2/governance/checkpoint_signature.py` verifies one checkpoint under caller-pinned deployment/key bytes. Do not change those digest meanings. New operator records should reuse `lib.content_digest.canonical_json_bytes(..., allow_nan=False)`, the existing Governance canonicalization path, with duplicate-key, unknown-field, boolean-as-integer, non-finite, noncanonical-byte and size rejection. A new serializer or new spelling for checkpoint-body digest would create ambiguous custody.

The host root has `archive/` inaccessible to containers and `read/` mounted as a read-only directory. A root-owned operator publisher holds a bounded exclusive `portalocker` lock under `archive/` while reconciling and publishing. All path components and files must be opened without following symlinks and checked for regular-file identity, size and owner/mode before trusting content. The actual root path/filesystem and independent backup destination are still deployment-specific.

## Proposed canonical records

Both records are UTF-8 canonical JSON, exact-key objects, at most 8 KiB each, with lowercase `sha256:` digests, strict positive integer sequences and UTC-second timestamps. Their record digest is SHA-256 of the whole canonical record bytes; the digest is stored in the filename or referring record, not self-declared inside the object. Identifiers use the current registry's bounded identifier grammar. `operator_id` is an audit label, not proof of authorization; host access controls and the separately retained operator receipt establish who approved the action.

`governance.approved_deployment.v1` contains exact `deployment_id`, `approval_sequence`, `previous_approval_digest` (null only at genesis), `image_ref` in `repository@sha256:<digest>` form, `image_platform`, `registry_sequence`, `registry_file_digest`, `grant_event_key_id`, `checkpoint_key_id`, `approved_at` and `operator_id`. The image reference and platform are checked by the operator against the pulled/resolved image outside the container; the app cannot self-attest them. The registry digest is compared to the exact canonical registry file; the two key IDs must match its purpose-specific entries. Ordinary ISSUE/REVOKE publication does not create a new deployment approval. The first publisher implementation accepts only approval sequence 1; a later image, registry or key approval needs a separately reviewed continuity ceremony. The parser can recognize a well-formed successor record without authorizing its publication.

`governance.checkpoint_high_water.v1` contains `deployment_id`, `approved_deployment_digest`, `checkpoint_sequence`, `checkpoint_body_digest`, `checkpoint_file_digest`, `previous_checkpoint_body_digest`, `previous_high_water_digest` (null only at genesis), `signer_key_id`, `checkpoint_issued_at`, `recorded_at` and `operator_id`. `checkpoint_body_digest` equals `ParsedGrantCheckpointV1.checkpoint_digest`; `checkpoint_file_digest` hashes the exact signed envelope bytes. `previous_checkpoint_body_digest` must equal the signed checkpoint body's predecessor and the prior high-water body's digest. The signer must equal the approved checkpoint key ID. The high-water sequence must advance by exactly one; exact scope identities cannot disappear and each retained scope's grant-event sequence cannot decrease in the ordinary publisher path.

`archive/approved/` and `archive/high-water/` contain create-once sequence-named records and retained checkpoint envelope bytes by their raw digest. The preflight enumerates a contiguous chain from genesis rather than trusting a mutable `latest` pointer. `read/approved-deployment.json` and `read/high-water.json` are public copies of the latest respective archive records. `read/governance-verifiers-v1.json` and `read/grant-checkpoint.json` are the pinned registry and current checkpoint. A wrong or unavailable copy, missing chain entry, duplicate sequence, divergent digest or unrecognized file type denies; the operator reconciles it without inventing a lower high-water. Root-owned files can still be replaced by host root, so this is a host-local trust boundary rather than a cryptographic proof against privileged host rollback.

## Initial enrollment and offline v1 publication candidate

Initial enrollment uses a signed empty-scope checkpoint at sequence 1 and a database with no Governance grant heads. The full scanner must verify that exact empty state before the first approved/high-water records are durably retained. Any nonempty pre-enrollment ledger needs a separately reviewed import ceremony; this proposal does not silently bless it as genesis.

For v1, perform grant import and checkpoint publication while the app and its workers are stopped. This reuses the project's M7 offline-fence operating pattern and avoids a half-published public pair being served during normal operation. Before restart, the publisher and startup gate still require independent verification; the existing PostgreSQL import/scan fences remain defense against cooperating concurrent processes. Online grant administration and zero-downtime publication are deferred until a forced interleaving proof covers all public-copy transitions.

Under the operator lock, the proposed publication sequence is:

1. In the normal path, verify archive chains, exact public copies of the previously published records, registry/image approval and database schema. Verify the submitted signed checkpoint with the approved purpose key. Compare it to the previous retained checkpoint, then run the existing full-chain scanner against the committed database. If a new grant event was imported but the checkpoint is missing, stay stopped/quarantined. If the archive already contains a newer entry than the public copies, enter the separate reconciliation path below before accepting another candidate.
2. Write the candidate checkpoint to a same-directory temporary file in `read/`; flush and `fsync` the file. Create the retained exact envelope and new high-water record under `archive/` with create-only semantics; flush and `fsync` both files and the affected archive directories. Never overwrite an earlier sequence file.
3. Publish a temporary public high-water copy using file `fsync`, same-directory rename and directory `fsync`. Then rename the complete checkpoint candidate over `read/grant-checkpoint.json` and `fsync` `read/` again. The two public names are not atomically replaced together. Any mixed pair must fail closed. Retain the old checkpoint in `archive/` for investigation.
4. Reopen all public paths, compare exact bytes/digests with the latest archived records and rerun the full-chain scanner. Only a successful operator preflight may start the activated app; that app independently verifies its read-only schema and full grant chain before readiness.

On crash or retry, the operator does not decrement the archive high-water or require the possibly stale public copies to match before reconciliation. It validates the complete retained chain, compares the latest retained entry and envelope bytes with both public files, republishes only those exact retained bytes if needed, and reruns scanner/preflight. A missing retained candidate or divergent database quarantines. An archive write that was not durably completed cannot authorize current publication. File and directory `fsync` are both required for the intended crash ordering; [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) distinguishes file contents from parent-directory entries, and [rename(2)](https://man7.org/linux/man-pages/man2/renameat2.2.html) provides atomic destination-name replacement on the same filesystem.

## Runtime and test consequences

The current `GovernanceGrantRecoveryScanner` and `CheckpointedShowrunnerGrantReader` compare a signed checkpoint to the database but do not compare its raw file/body digest to the operator high-water. An activated composition must add a pinned loader that checks the approved deployment, registry and public high-water copies and loads a checkpoint matching both digests. It must read the high-water again after opening the checkpoint (or otherwise prove one stable view); any cross-file change denies rather than returning an old/new mixture. The full scan must use the same loader. The existing `GovernanceCheckpointFile` can supply the bounded fresh checkpoint bytes; it is not an archive verifier.

Required tests before implementation acceptance: canonical record vectors and adversarial parser cases; genesis with nonempty ledger denial; duplicate/missing archive sequence; unknown or switched key; raw-envelope versus body-digest confusion; wrong image/registry; old database plus old checkpoint against retained newer archive; each publication crash point and idempotent retry; public-copy mismatch; symlink and mode/owner failures; two publishers contending on the host lock; no app or worker readiness on any failed preflight. Run them with test-only Ed25519 keys and a disposable PostgreSQL restore. The actual host filesystem, access rules, independent backup/restore, image digest pin and key rotation remain external gates.
