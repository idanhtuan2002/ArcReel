# R2 idea-to-story authoring

Status: DRAFT_FOR_HUMAN_REVIEW. This document does not release implementation or authorize live provider spend.

## Outcome and first product slice

The operator enters an idea, language, genre and bounded target length; selects Claude, an OpenAI model or a local model; reviews an outline; then obtains a complete, editable manuscript stored through the R2 Narrative lifecycle. The interface shows saved chapters, progress, failures and export. Restarting must preserve every admitted draft and revision.

The initial acceptance corpus is one Vietnamese short story with three chapters and a visible ending. This bounds the first demonstration; the interface must expose its actual configured limits. Arbitrary-length novels and literary or commercial quality are not acceptance claims. A provider's successful transport response is not proof that the story is complete or coherent.

The Human requested model choice on 2026-10-17 after the idea-to-complete-story proposal. This selects a configurable provider direction, not a specific model ID, paid budget or API credential. Model IDs are selected from operator configuration rather than fixed in this document.

## Provider behavior

One common authoring service consumes host text-generation ports. The operator selects one configured provider/model per generation step. Each output records the executed provider/model and request-context identity; changing a selection affects future steps and never rewrites prior output provenance. There is no automatic cross-provider fallback.

| Choice | Candidate connection | Required qualification |
| --- | --- | --- |
| OpenAI models | Existing OpenAI text/backend configuration | Supported token parameter, model limits, response termination, route admission and accounted usage |
| Claude | Host text adapter for the Anthropic API; reuse compatible transport only if fixture qualification succeeds | Authentication, system instructions, valid sampling parameters, termination, usage and bounded structured-output handling |
| Local model | Configured local endpoint, initially Ollama's OpenAI-compatible chat interface | Installed model, context/output limits, termination, schema validation, cancellation and zero cloud fallback |

Official references checked on 2026-10-17:

- [Anthropic OpenAI SDK compatibility](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk): a compatible transport exists, but `response_format` is ignored and system/developer messages are hoisted. Compatibility is not native-feature parity. The shared OpenAI backend cannot be assumed Claude-compatible without checking emitted parameters; a focused native adapter is the fallback if the existing seam cannot represent the required semantics.
- [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility): only a subset is supported; local examples use `http://localhost:11434/v1/`. The configured endpoint and installed model must be tested, not inferred from the provider label.
- [OpenAI billing separation](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform): using an OpenAI model here requires API access; a ChatGPT subscription is separate.

No API keys appear in prompts, output provenance, browser storage or diagnostic logs. Existing host credential storage remains owner. Local execution stays on the selected local endpoint. No provider is labeled available until its real configuration passes qualification. Lack of one provider must not prevent use of another qualified provider.

## User workflow

1. Create/select an authenticated project. Enter idea, constraints, genre, language, chapter count and bounded length. Select a configured model and explicit run limits.
2. Generate outline and character proposals. Save them as project artifacts using existing host ownership. They are not yet an approved NarrativePlan or Canon.
3. The operator selects/edits the outline and supplies the required explicit Human decisions through real host authority. Bootstrap Canon/Plan/Scene bases through their existing owners; never fabricate Human approval or fixture identifiers. If any production authority adapter is absent, stop at that named composition gap before generation is described as R2-bound.
4. Compile exact scene context and generate chapters/scenes in order. Each model output becomes a scoped immutable R2 candidate. Previously generated, unaccepted prose can supply explicitly labeled draft context; it cannot silently become accepted narrative or Canon truth.
5. Save after every successful step. Display each stored chapter and its revision history. Editing or requesting a rewrite appends a revision; selecting a branch is explicit.
6. Check required chapter coverage, ending and continuity findings against the selected outline. Show unresolved findings to the operator. Repair has a finite configured budget, never an unbounded review/write loop.
7. Export the selected manuscript as UTF-8 text/Markdown through host artifact ownership, with the exact selected chapter/revision identities. Reopen must reproduce the exported content. Export does not admit screenplay, approve Canon, generate video or publish externally.

## Runtime, persistence and failure boundaries

The host remains owner of runtime tasks, artifacts, execution and credentials. R2 remains owner of Narrative evidence and decisions. Do not add a second authoritative story database, queue or scheduler. An authoring status projection must be reconstructible from existing owners and exact saved step evidence. Qualify the task/execution schema before deciding whether an additive task type is sufficient; a required new authoritative aggregate or incompatible migration returns to design review.

Persist each step's immutable input and execution identity before model I/O. No database transaction spans provider I/O. Finalize saved output and its linkage to the runtime step consistently, and recover a returned output before considering another submission. Repeated commands return an existing result when available. An ambiguous paid result becomes a visible unresolved state; resume must not silently send the same request again.

Successful model output may be followed by a failed save, cancellation or restart. Acceptance must probe each boundary. Keep previous admitted chapters and show a recoverable error; never overwrite them or mark a partial manuscript complete. User-requested regeneration is a new step with explicit identity and budget.

Enforce chapter count, input context, output token, call-count and run-cost ceilings before dispatch. The implementation plan must trace backend/SDK retries and structured-output fallback so hidden retries cannot defeat the ceiling. Unknown usage/cost is reported as unknown, not zero. Stop when the remaining budget cannot authorize the next call.

Plain-text truncation currently has log-only behavior in shared helpers. The new authoring boundary must reject truncated output as a completed chapter, preserving any recoverable returned bytes as an incomplete artifact. Do not globally change unrelated text workflows to implement this rule. Structured outline output must be validated locally even if a provider advertises structured responses. No unlimited format-repair loop is allowed.

## Product surface and implementation boundaries

The delivered surface is an authenticated host authoring page, with idea entry, provider/model selection, outline review, generation progress, chapter editing/history, resume and export. A CLI can qualify the first real scene internally but does not satisfy the requested user path by itself. Use existing host routes, UI components, localization and provider settings where applicable. All supported locales must receive user-facing strings. Select free ports explicitly; do not interrupt the other project using 5173.

Candidate ownership areas for the implementation plan: host authoring service/router and frontend feature; narrowly qualified additions to text backend capabilities; existing host task/artifact/execution composition; R2 Narrative context/evidence adapters; affected tests and operator instructions. An exact path list and migration decision must be established in the implementation plan after adapter qualification, not invented here.

## Acceptance and bounded verification

- Demonstrate a real idea-to-ending short story through one operator-selected configured provider, saved as actual R2 candidates/revisions on real approved bases. Show an operator edit, close/restart/reopen, and exact selected manuscript export.
- Verify all three provider adapters using deterministic transport fixtures for request parameters, structured output, truncation, usage, errors and cancellation. A fixture pass is not a live provider pass; report live qualification separately for each configured provider.
- Verify successful-step resume, duplicate commands, save failure after output, crash windows, ambiguous responses, finite repair/retry behavior, budget exhaustion, model changes, scope isolation and stale approved bases. Use PostgreSQL interleavings for changes that depend on locks or transactions.
- Run required affected-domain static, migration, browser and backend gates on the exact integration candidate. Do not repeat historical full suites without a changed risk or release gate.
- At most one independent final acceptance review and one evidence-driven repair; no automatic re-review loop. No implementation acceptance or production activation follows from this design document.
