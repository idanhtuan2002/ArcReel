# R2 M8-C ProductionBinding authority and spatial promotion design candidate

Status: **proposed**. Depends on ADR-0102 review and acceptance. This packet extends the accepted M8 spec only at the missing `PRODUCTION_BINDING` authority seam; it does not redefine M8-A's artifact-slot path or release M8-C C2.

## Why this packet exists

The frozen domain model makes `ProductionBinding` the semantic-to-production bridge. The accepted M8 spec targets that bridge for `SpatialCandidate`, and ADR-0095 requires a persistent CAS writer before promotion. The inspected R2 source has only in-memory binding and target values; the M8 preview API rejects the binding target; the prompt planner has no typed spatial input. [Source inventory](../../research/2026-09-30-r2-m8c-production-binding-authority.md) and [consumer comparison](../../research/2026-09-30-r2-m8c-consumer-options.md) record the bounded evidence.

## Authority model

| Object | Owning write path | Identity and immutable content | Read rule |
| --- | --- | --- | --- |
| Production target | Production Preparation | project, `SCENE`/`SHOT`, ID, registry-owned version, canonical `SceneSpec`/`ShotSpecV2` digest, exact screenplay admission ref and derivation version | Current registry head plus exact immutable derived version; a shot also resolves its scene in the same project |
| Production binding | Production Preparation | project, binding ID, monotonic version, exact v1 body digest, exact target type/ID/registry version/digest, optional spatial-set ID/digest, envelope digest | Head for admission, exact version for snapshot/readiness |
| Spatial constraint set | Production Preparation via M8 authorized promotion only | immutable ID, digest, exact candidate revision/digest, selected visible assertion IDs, source media IDs/digests and source spans | Exact set only through a binding version |
| M8 candidate/preview/authorization/receipt | M8-A authority | existing IDs and digests plus typed spatial proposal and binding expected head | Exact revision and preview, same transaction as binding update |

Target registration is necessary because a binding's `target_id` otherwise has no checked production identity in the inspected host. The first supported target family is Take-derived scene/shot. The registration command takes an exact `AdmittedScreenplayRef`, re-reads its current admission head, decision and content hash through the same repository-level checks used by `ApprovedScreenplayReader.get_exact_admitted` but bound to the registration session, and compares the command's full `AdmittedScreenplayRef`, including `profile_ref`, with the stored admission projection. The public reader method and `TakeDirectorAdapter` currently pass only screenplay and decision refs; the bound registration path must add the profile check rather than treating the caller's profile as authority. It then runs `TakeDirectorAdapter` against that verified screenplay through its reader port, requires the derived target's `approval_status=APPROVED`, and stores the selected scene/shot digest plus full admission provenance and derivation version. The existing public reader's UoW cannot be nested into the registration transaction. Registration verifies shot-to-scene identity in the same derived result; it records that proof but cannot independently approve a caller-constructed target. Other Director families are unsupported until their exact upstream authority proof is reviewed. Target and binding creation stay outside M8 promotion.

`TakeDirectorAdapter` currently stamps `SceneSpec.version=1` and `ShotSpecV2.version=1` for every derivation. These are embedded source-body versions, not durable registry versions. The target registry therefore owns a separate monotonic version and head per `(user_id, project_name, target_type, target_id)`. A registration with the same current admitted-screenplay ref, derivation version and derived canonical digest is an exact replay and returns the existing version. A changed admission, derivation version or digest appends `head+1` and advances the head under a row lock; the immutable earlier version remains addressable. A changed result under the same command ID is a conflict. The registry refuses an older admission after a newer current admission and never infers version from the adapter's hardcoded `1`. A shot version stores its exact scene registry ID, version and digest from the same derived bundle. The binding points at the registry version/digest, and every consumer rechecks both the current target head and current upstream admission before use. This rule must be exercised with two admitted screenplay versions deriving the same target ID but different content.

The first spatial source family is exactly two immutable still frames, one `MASTER` and one `REVERSE`, derived from two distinct project-scoped approved M7 episode-video master heads. The current Gate C approval route and projection are episode-video-specific; the inspected source does not establish an image-master approval route. Each source binding includes the parent artifact key, master version, candidate ID/content digest, zero-based decoded frame index and decoder/recipe version, derived frame candidate ID/content digest, and view. The parent master approval is the media authority; the frame is an immutable derivative, not an independently approved image master. A separate Production Preparation `SpatialPairAdmission` is required to attest that these exact two frames are suitable front/reverse views of the same target location, from one camera point with the reverse view rotated approximately 180 degrees. Gate C's two independent video approvals cannot attest that relation. The server's scoped `verify_masters` must require a matching projection for each current parent, since `DatabaseMasterResolver.get_exact` alone accepts a missing legacy projection; the exact parent snapshot and `CandidateObjectRepository.get_exact` must then match parent and frame objects/digests. Execution rehashes frame bytes before sending them to the model. A frame without approved-parent lineage or pair admission, or a mutable asset URL, is unsupported for production promotion. The [source comparison](../../research/2026-09-30-r2-m8c-spatial-source-custody.md) records why this first path is selected and what fixtures are still required.

The extraction service owns an immutable `SpatialFrameDerivationReceipt` keyed by `(user_id, project_name, frame_candidate_id)`. It records the exact parent artifact key/master version/candidate ID/content digest, zero-based decoded frame index, recipe and decoder version, frame byte size/content digest/media-probe digest, created-at and command digest. `frame_candidate_id` is derived from a domain-separated hash of parent identity, recipe and frame digest. The server first verifies the current approved parent and source bytes, selects one frame by its validated decoded index with pinned settings, and publishes it with an atomic no-overwrite operation before registering the candidate object and derivation receipt in one database transaction. `prepare_candidate` cannot be used unchanged for frame publication: its precheck followed by `os.replace` can overwrite a concurrently created destination. Before receipt commit, a sorted master-head lock and scoped projection check must confirm the pinned parent is still current, and the service must rehash parent and frame bytes. A replay with the same command/body verifies the existing file and receipt; a changed body conflicts. A file publication completed before database rollback may leave an unregistered immutable object; retry registers it only after exact byte/recipe/parent verification, and ordinary reads refuse it without a receipt. No client can create or edit this receipt. Preview and promotion rehash the receipt, recompute the frame identity, verify the registered object and parent master head, and refuse any mismatch.

The [frame-selection research](../../research/2026-10-03-r2-m8c-frame-selection.md) proposes decoded frame ordinal as the exact selector for the initial recipe, with bounded index and decoder identity; timestamp-only seeking is outside this first source path. The local three-frame extraction probe establishes feasibility on one FFmpeg build, not cross-build byte stability or source custody. The output digest and receipt remain authoritative.

`SpatialPairAdmission` is a separate immutable decision plus current head keyed by target/location binding. It stores exact target registry version/digest, `LOCATION` binding ID and stable core-ref digest, ordered MASTER/REVERSE frame-derivation receipt IDs/digests, reviewer identity/scope, evidence refs for view coverage/camera-center/yaw suitability, decision `APPROVE` or `REJECT`, decision time, version and command digest. Only an authorized human decision can set `APPROVE`; model text and two independent video approvals cannot. A changed target, binding core refs, frame receipt or parent master head invalidates current pair suitability; a later decision appends a version. The preview includes pair admission ID/version/digest, and promotion locks/rechecks its current head before translating any seam or direction constraint. If the pair is absent or rejected, the candidate remains evidence only and binding promotion stops. The first fixture must include an unsuitable pair rejection as well as an approved same-location pair; the approval is an accountable suitability decision, not a claim that an algorithm has proven camera geometry.


The proposed [source digest vectors](../../research/2026-10-03-r2-m8c-source-digest-vectors.md) fix canonical bytes for frame identity, frame derivation receipt and pair decision. The frame candidate ID is `m8f:` plus the full hex of its domain-separated identity digest; a receipt uses that candidate ID as its key and has a separate digest. Pair evidence and human authorization carry exact refs **and digests**. These examples are serialization design, not proof of media custody or authority.

The proposed [binding snapshot vectors](../../research/2026-10-03-r2-m8c-binding-snapshot-fingerprint.md) fix one v1 binding body and its body/envelope/snapshot digests. An adversarial variant changes only the spatial-set digest under the same body and version to prove digest propagation; an authority reader must reject that mutation as corruption, not accept it as a second legal binding version.

The binding version envelope preserves the v1 `ProductionBinding` field schema and does not change existing fixture serialization. It adds exact target type/ID/registry version/digest and spatial-set identity/digest around that body. The target type/ID in the envelope must equal the v1 body, and its target version/digest must equal the scoped target registry row and the matching snapshot target entry; a target advance invalidates that binding version for current admission. `LOCATION` is the only role eligible for the first M8-C spatial update. An update increments the body's `version` and copies every other v1 field unchanged; it cannot change the target, semantic/production refs, role or asset refs. Other binding edits use a separate Production Preparation command and their own typed validation.

Every stored digest uses a named domain and canonical JSON version. Digests cover all identity and content fields, including source media references, source spans, assertion IDs, classifications, locks and normalizer version. The snapshot digest covers ordered `(binding_id, version, envelope_digest)` tuples and the exact target-version digests. Digest input and bytes must be fixed in a test vector before schema implementation. A reader rehashes stored bodies rather than trusting a digest column.

## Spatial evidence and mapping

A validated candidate revision retains the donor-derived visible/inferred/gap distinction, overlap deduplication, seam topology, direction exclusions, source references and normalizer version. The accepted `SpatialAssertion` had generic `relation` and `subject_refs`; the C1 work in progress adds optional typed `source_spans` while preserving old assertion JSON bytes. A span for the first two-frame path is a normalized object-level image rectangle (`source_ref`, `source_digest`, `view`, `x0`, `y0`, `x1`, `y1`, each coordinate within `[0,1]`, positive area) tied to an exact derived frame digest and its approved M7 video-parent lineage. A shared side anchor may carry one rectangle from each view. A coarse whole-image or side-crop label is insufficient to establish that an individual asserted object is visible. An empty or unresolvable span fails closed. The provider/model result is evidence only.

The public M8-A append route currently accepts a caller-authored `ExplorationRevision`; it cannot establish the required spatial execution/source identities. The generic route and service must reject `SPATIAL` revisions before any write. A server-owned spatial completion service reads a terminal successful M7 attempt, exact raw-response bytes/digest, model/route and prompt/schema fingerprints and frame derivation receipts; it rehashes the bytes, validates the raw schema before normalization, constructs the candidate from server-resolved source identities and appends through M8's existing CAS/idempotency store. Failed/cancelled/unknown attempts, missing/corrupt source, schema failure or normalization mismatch create no revision. Pair admission can follow candidate creation, but must precede promotion. The [append-boundary research](../../research/2026-09-30-r2-m8c-spatial-append-boundary.md) records the current public seam.

The proposed first completion fixture stores bounded exact raw/overlap response bytes in one immutable scoped database sidecar linked to the M7 execution and M8 revision, and places its canonical receipt digest in the newly completed `SpatialPayload`. This keeps provider bytes out of the general candidate response while allowing receipt, revision and command receipt to commit together. Every authority reader must load the sidecar with the revision and rehash its bytes and body; a missing or mismatched sidecar invalidates that spatial revision for promotion. The [completion-evidence comparison](../../research/2026-10-04-r2-m8c-spatial-completion-evidence.md) and fixed [vector](../../../tests/fixtures/r2/m8c_spatial_completion_evidence_vector.json) bound the proposed identity shape. This is a design selection for the first fixture, pending byte limit, scoped FK/lock order, PostgreSQL interleaving tests and independent review; no sidecar or payload link is implemented.

The pinned DramaClaw prompt explicitly instructs its model not to output bbox or original-image coordinates (`scene_spatial_contract.py:274-280`). That behavior cannot satisfy the accepted M8 source-span requirement. R2's spatial prompt/schema must request the rectangle, and its validator must reject a `VISIBLE` item without one. The donor differential should still compare selected overlap/direction normalization on the same spatial fixture. This source-span change is an intentional donor correction: retain a donor fixture that lacks the span and an R2 regression fixture that rejects or downgrades it rather than fabricating coordinates. It must be marked `IMPROVED` only after the exact fixture/test evidence passes.

The preview request names an existing binding and selected assertion IDs. The server derives the typed spatial proposal; a client cannot author the resulting relation, source digest, lock or `ProductionBinding` body. The adapter validates every selected assertion as `VISIBLE`, resolves its exact M7 master/candidate digest and span, rejects contradictory direction/seam constraints and records omitted `INFERRED`/`GAP` rows in the impact view. The proposal's canonical digest is part of the preview. The human authorization binds that digest and an expiry. The resulting immutable set carries structured constraints and provenance, not a prose prompt fragment. The first eligible mapping is a named object preserved on a specified `front`/`back` wall, or a shared physical anchor on a `left`/`right` seam. The wall is a server-stamped field in the normalized assertion detail; client/model-authored `wall` is overwritten during C1. Other relation forms fail preview until a separate typed mapper is reviewed. `INFERRED` and `GAP` rows remain visible as warnings only.

The candidate normalizer and its donor differential can be implemented before this authority. The exact selected donor behavior is spatial normalization in `scene_spatial_contract.py`; the donor 360 builder is a consumer comparison, not automatically part of the selected parity surface. The parity contract must state this boundary and run same-fixture donor/R2 behavior for every selected material row under R2-DEC-031. A donor correction needs a failing donor fixture and stronger R2 expected result.

## Write and replay protocol

The Preparation writer uses one database transaction and one `AsyncSession`, operated sequentially within one task. It scopes every query by user and project and verifies actor and project access before writing. A target-registration command locks its command key, then invokes a transaction-bound screenplay reader through `TakeDirectorAdapter`; that reader locks and verifies the current screenplay-admission head before deriving the scene/shot bundle. Registration then locks target heads (scene before shot), appends immutable target versions and advances their heads without opening a second unit of work. Binding create/update locks its command key, then the admission and target heads, then the binding head; it revalidates exact target/media content and expected binding version under those locks before appending one immutable version and advancing the head. A request with expected version zero can create a binding only through the separate Preparation create command. M8 always requires an existing positive head. A writer needing M7 master or candidate rows takes them only after all earlier heads it uses in the order below.

For M8 promotion, lock order is M8 command key → candidate head → preview → screenplay-admission head → target heads (scene before shot) → binding head → spatial-pair head → M7 master heads in ascending artifact-key order → immutable candidate and frame-derivation rows in ascending candidate-ID order. Pair admission and generation-attempt planning use the same admission → target → binding → pair → M7 subsequence whenever they touch more than one family; no writer may acquire an earlier family after a later one. The order extends the accepted M8 command/candidate/preview prefix without changing the artifact-slot promotion arm. Every query is scoped by user and project. The target registry, pair admission, frame derivations and M7 master rows must be checked through the same PostgreSQL session as M8, including current upstream screenplay-admission head verification; a separate `ApprovedScreenplayReader` unit of work cannot provide an atomic currentness check during promotion. The implementation must expose transaction-bound read/lock ports for the adaptation admission fold, target registry, pair head, M7 master resolver and candidate/derivation repositories. Extract the existing exact-admission fold checks into one repository-level routine shared by the public `ApprovedScreenplayReader` and a reader bound to the promotion or registration session; the bound reader must neither commit nor close that session. `TakeDirectorAdapter` already accepts a reader port and should reuse the bound reader for target derivation. The current unlocked `DatabaseMasterResolver.get_exact`/`CandidateObjectRepository.get_exact` cannot be used as the promotion proof. The master port must require a matching legacy projection for each locked episode-video head and revalidate candidate object/digest in that transaction. If a legacy projection cannot provide a transaction-consistent read, the source is unavailable for promotion until that projection is fenced by its owning authority; an eventual read is insufficient. The transaction checks authorization scope, candidate revision/body digest, selected assertion classifications, preview digest/expiry, binding version/envelope digest, target version/digest, pair admission, frame receipt/bytes, source media digests and the constraint proposal digest under those locks. It stages the immutable constraint set and binding version, authorization, promotion receipt and command receipt, then commits once. An exact command replay returns its stored result before currentness checks; the same command ID with a different body fails. Storage failure rolls back all staged rows. Lock acquisition and transaction ownership must be shared with the existing M8 promotion adapter rather than nested commits. Forced PostgreSQL interleavings must cover registration versus re-admission, binding create/update versus promotion, pair replacement, frame corruption, M7 master advancement and generation-attempt planning; each must prove no stale receipt or deadlock. This is the proposed cross-writer order until the design gate accepts it.

The preview read is non-mutating. It binds the exact expected head and names effects on readiness/fingerprints and the prompt consumer. The current untyped `impact` field remains explanatory only. Promotion may not turn a gap or an inferred claim into a visible production fact.

### Spatial wire and persistence arm

Keep the accepted artifact-slot `PromotionPreview` and `PromotionReceipt` models, bytes and digest domain unchanged. Add a separate `CreateSpatialPromotionPreviewRequest` endpoint with `candidate_id`, `candidate_revision`, `binding_id`, `expected_binding_version`, a nonempty ordered `selected_assertion_ids` tuple and `command_id`. The server computes a `SpatialConstraintProposal` from the selected visible assertions and their server-stamped wall, with typed relation kind, subject ID, wall, exact source refs/spans, applicable seam/direction/duplicate locks and candidate-normalizer version. It cannot carry a binding body, and no client-provided relation text or digest is accepted. Its digest uses a new domain and canonical version. The server resolves the binding and sources, never trusts client digests, and returns a `SpatialPromotionPreviewV2` containing the existing preview identity fields plus the binding envelope/target/source/proposal digests. The authorization's existing `preview_digest` refers to the V2 digest. Binding target requests to the existing generic preview route remain unavailable.

The existing `m8_promotion_previews` row supports a `PRODUCTION_BINDING` target but has no typed proposal columns. Add a `m8_spatial_preview_bindings` sidecar keyed by scoped `preview_id`, holding the V2 schema discriminator, canonical typed proposal, selected assertion IDs, binding and target identities/digests, and ordered source identities/digests. The V2 digest covers base-row fields plus the sidecar; the repository requires exactly one sidecar for a binding target and none for an artifact slot. No binding preview row existed under ADR-0095, so old preview bytes remain untouched. Add an analogous scoped `m8_spatial_promotion_results` sidecar keyed by `receipt_id` with binding version/envelope digest and constraint-set ID/digest; the existing receipt row's `result_master_id` stays null. A V2 result reader rehashes both rows. Migration and corruption tests must enforce coupling at read and database constraint boundaries. The existing M8 command-key namespace is reused, so replay cannot cross wire arms.

The V2 wire has these field groups; all models forbid extra fields. `SpatialSourceBinding` is `(parent_artifact_key, parent_master_version, parent_candidate_id, parent_content_digest, frame_derivation_receipt_id, frame_derivation_receipt_digest, frame_candidate_id, frame_content_digest, view)` in the caller's project. Internal filesystem `object_ref` values never enter the public wire or its canonical digest; the server resolves the opaque candidate ID. `SpatialConstraint` is `(assertion_id, relation_kind, subject_ref, wall, source_spans)`, with `relation_kind` limited to `PRESERVE_ON_WALL` for front/back and `SHARED_SIDE_ANCHOR` for left/right. `SpatialConstraintProposal` is `(schema_version="2", candidate_id, candidate_revision, candidate_payload_digest, constraints, seam_locks, direction_locks, duplicate_warnings, normalizer_version, pair_admission_id, pair_admission_version, pair_admission_digest, ordered_sources)`. Constraint order follows the selected assertion order; selected IDs must be unique, and each selected assertion must have exactly one subject and server-stamped wall. Locks are copied from the exact candidate revision, never supplied by the client. `SpatialPromotionPreviewV2` is `(schema_version="2", base_preview, selected_assertion_ids, binding_id, expected_binding_version, binding_envelope_digest, target_type, target_id, target_registry_version, target_digest, proposal, proposal_digest, ordered_source_digests, preview_digest)`. The base preview's `target_ref` equals `binding_id` and its `expected_target_version` equals `expected_binding_version`. A V2 reader rejects any mismatch across these repeated fields. `SpatialPromotionReceiptV2` is `(schema_version="2", base_receipt, binding_id, binding_version, binding_envelope_digest, constraint_set_id, constraint_set_digest, receipt_digest)`. The base receipt's `result_artifact_ref` is the exact binding-version ref, `result_digest` equals `binding_envelope_digest`, and `result_master_id` is null. The M8 PROMOTE command receipt's `result_kind` is `SPATIAL_PROMOTION_RECEIPT_V2` and its `result_digest` is `receipt_digest`; replay rehashes both base and sidecar before returning.

Every V2 digest uses the existing canonical JSON byte encoder but a distinct explicit envelope: `digest_canonical({"domain":"r2.m8.spatial.proposal.v2","canonical_version":"1","body":proposal_without_digest})`, analogously `r2.m8.spatial.preview.v2` over the complete V2 preview except `preview_digest`, and `r2.m8.spatial.receipt.v2` over the complete V2 receipt except `receipt_digest`. Binding, target, source, constraint-set and snapshot domains must each have their own named envelopes and fixed byte/digest fixtures before migration implementation. On write, a scoped FK links each sidecar to its base row; deferred PostgreSQL constraint triggers require exactly one spatial sidecar when the base target kind is `PRODUCTION_BINDING` and zero for `ARTIFACT_SLOT`, including on delete/update. The same rule applies to receipts. Application readers enforce the coupling and rehash both halves even when database constraints pass. A migration must prove existing artifact-slot rows acquire no sidecar and preserve their original digest and replay behavior.

## Read and consumer protocol

The snapshot resolver returns exact binding versions and verifies envelope, v1 body, spatial set and target digests. ProductionReadiness evaluates this resolved set and records the snapshot ID. Content fingerprinting includes the snapshot digest so a spatial-only update changes the fingerprint. A stale readiness snapshot cannot authorize later use. Existing pure Golden fixtures continue to work as offline fixture inputs; they are explicitly tagged as such and cannot be used as live authority reads.

The R2 prompt planning/compilation seam takes a typed resolved spatial set from an exact `LOCATION` binding, emits only supported visible constraints, and records the binding snapshot in the prompt plan/fingerprint. An inferred region or gap is represented as a coverage warning, never as a positive scene fact. Same-fixture tests must show that the binding changes the compiled semantic prompt and that omission does not invent topology. The current M4 `ExecutionDecision.request_semantics_hash` omits `positive_prompt`; a direct probe changed only that field and observed an unchanged decision ID/hash but a changed compiled payload. Consequently the consumer binds the complete normalized prompt-plan and compiled-request digests through task evidence and the M7 host request, and a spatial-only prompt mutation must fail replay against the prior snapshot. The M4 decision hash cannot stand in for either digest.

The consumer gate also requires one reachable application entrypoint for a Take-derived shot. It must resolve the current approved target and binding snapshot, evaluate readiness with that snapshot, recheck currentness inside admission rather than trusting the caller-supplied `readiness_is_current=True` default, compile the prompt with visible spatial constraints, and bind the snapshot identity and compiled request digest through queueing and M7 attempt submission. A stale or corrupt read fails before provider submission. The existing `/projects/{p}/generate/video/{segment_id}` path accepts an independent prompt and disk script, so it cannot be treated as this entrypoint merely by calling `PromptPlanner` in a test. The existing queue's `reference_video` task rereads mutable script content at execution, so it cannot carry this exact snapshot either. A dedicated R2 shot-generation route and task type must persist the exact target/binding snapshot, compiled prompt digest, source media identities and command key; the worker re-resolves and revalidates them at claim and immediately before M7 attempt submission. No path may silently fall back to a caller prompt or disk script on mismatch. The route, task payload and worker/submit fingerprint are a public contract change and require independent review before use. M8-C acceptance requires a traced application-route-to-submit test, not only Golden-script output.

The first route is `POST /projects/{project_name}/r2/shots/{target_id}/generate`, with request `(command_id, expected_target_registry_version, expected_binding_snapshot_digest, execution_profile_ref)` and no prompt body. The response is `(task_id, target_registry_version, binding_snapshot_digest, host_request_digest)`. A new persisted queue type `r2_shot_generation_v1` carries `(user_id, project_name, task_id, command_id, target_type="SHOT", target_id, target_registry_version, target_digest, upstream_admission_ref, binding_snapshot_id, binding_snapshot_digest, ordered_binding_versions, spatial_set_digests, ordered_source_master_identities, prompt_plan_digest, compiled_request_digest, execution_projection_digest, provider_payload_digest, host_request_digest, execution_decision_id, execution_profile_ref)`. The selected versioned execution profile maps the decision's `(capability_id, descriptor_version)` to one actual registered M7 provider/backend model/endpoint/capability tuple and fails closed on any mismatch; the M4 capability ID is not assumed to equal the backend model name. The profile also proves the exact two-reference image modality and count: current M4 `VIDEO_OUTPUT` eligibility does not evaluate `input_modalities`, so a selected video descriptor alone cannot authorize this source shape. Route admission separately rejects unsupported control, modality, count, model, endpoint or profile version before queueing. The first Wan profile pins five seconds, 720P, a chosen ratio, watermark/seed policy and `prompt_extend=false` in the exact captured provider payload, validates decoded frame dimensions/format/opacity/size and prompt lengths, and refuses the route if its R2 backend arm cannot emit those fields. The current DashScope builder omits `prompt_extend` while the official API defaults it to true, so the existing offline payload alone cannot establish exact spatial prompt use. The route derives every field except command ID, expected identities and profile selection; it derives the provider-payload digest from pinned immutable media and stores the compiled request, runtime video projection, provider-payload digest and host request as immutable task evidence. The worker reconstructs and byte-compares these from verified media before submission, retaining the captured provider payload for the eventual callback. A repeated command with the same normalized request returns the same task; a changed body conflicts. Active-resource dedupe must also compare the full R2 snapshot/request fingerprint, so a different command cannot alias an older active task.

At claim, the worker re-resolves the queued snapshot, compiled request, runtime projection and host request. A final `admit_and_plan_spatial_attempt` transaction then locks/rechecks admission, target, binding, pair, source masters/frames and currentness in the shared order above, reconstructs the exact request digest and stages the M7 `PLANNED` attempt in the same PostgreSQL session before one commit. This commit is the currentness linearization point: a head change committed before it blocks planning; a head change after it leaves the already admitted attempt pinned to its immutable snapshot. No database lock spans the provider call. The current `ExecutionAttemptServiceImpl.plan_and_submit` commits `repository.plan` internally, so a separate precheck followed by the existing method is insufficient. After the admission commit, existing `AttemptSubmitter.submit` can continue an exact preplanned attempt through its replay/lease/fence path; the planner needs a reviewed shared attempt-identity construction contract, and crash-after-plan still needs integration proof. The [submit-boundary research](../../research/2026-09-30-r2-m8c-m7-submit-boundary.md) and [runtime-projection correction](../../research/2026-10-03-r2-m8c-runtime-submit-projection.md) record the current contract and required integration seams.

`DefaultPromptCompiler` emits a semantic `ProviderRequest` with `method_decision_ref`, while the live video backend constructs a different host payload from `VideoGenerationRequest` and `AttemptSubmitter` requires `host_task_ref=task_id`. An origin-only copy of the M4 payload cannot be the M7 submit request. A versioned R2 execution projection must map every required compiled semantic, reference and generation option into one exact runtime video request or fail closed. It records the original method-decision ID, compiled request digest, projection digest, prompt-plan/binding snapshot digests, chosen route and exact source-media identities in task evidence. A typed R2 arm of the live video adapter builds the M7 `ProviderRequest` from the **same captured media bytes and runtime request** used to construct the provider payload, with `host_task_ref` and an R2 identity envelope in `execution_options`; it must refuse a rebuilt payload or empty R2 options. The first supported backend route constructs its provider payload once from pinned inputs, binds the canonical payload digest and exact endpoint into the host request, and submits those captured bytes after M7 fencing. The exact host request JSON is what M7 hashes as `request_digest`, and preplanned replay must match that digest, route and task before the provider call. The R2 attempt-submission fingerprint has domain `r2.m8.spatial.submit.v1` over `(task_id, command_id, target_registry_version, target_digest, binding_snapshot_digest, prompt_plan_digest, compiled_request_digest, execution_projection_digest, host_request_digest, execution_decision_id, provider, model, endpoint, adapter_version, ordered_source_master_identities)`. Its constituent snapshot, compiled-request, projection, provider-payload and task identity fields enter the host request's versioned `execution_options`; the fingerprint itself is computed **after** the final host request digest and stored in immutable task evidence. This avoids a digest cycle. The R2 submit guard rederives and compares the fingerprint while M7's existing full-request digest binds the identity envelope, without assuming a new attempt column. The worker rehashes mutable-path media before payload capture; a change after capture cannot alter the bytes submitted. The current M4 `_request_fingerprint` omits `execution_options`, and `compute_execution_fingerprint` is called with empty generation settings in the Golden host adapter, so neither proves this identity. The R2 arm needs a versioned fingerprint function rather than silently changing legacy hashes. The same snapshot digest must enter a versioned content fingerprint and readiness receipt. The current body-only `compute_content_fingerprint` does change when the proposed spatial promotion increments `ProductionBinding.version`, but it does not bind the spatial-set digest or verify its bytes; a changed set under a copied or corrupt binding body is not covered. Tests must distinguish version-bump detection from exact set-content binding: an isolated pure fingerprint vector changes when only the spatial-set digest changes with the v1 body held fixed, while an authority read rejects such a mutation of an existing immutable binding version. A legitimate later promotion advances the binding version and set digest; its new readiness receipt and exact digest must trace from route through task claim to M7 submit.
