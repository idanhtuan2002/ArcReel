# M8-C LOCATION binding creation design

**Status:** proposed narrow authority packet. It refines ADR-0102 for the first Take-derived Shot and two approved frame sources. It does not accept binding CAS, pair suitability, spatial promotion or a generation route.

## Purpose and current basis

Create one durable `LOCATION` `ProductionBinding` for a current Take-derived Shot without trusting caller-authored target IDs, media IDs or readiness flags. Preserve the v1 `ProductionBinding` body and Golden fixture bytes. Store a versioned, scoped envelope that ties the body to an exact target/admission and two current frame receipts. A later human `SpatialPairAdmission` decides MASTER/REVERSE suitability; creation alone is not READY.

The code basis is the accepted target-ID consumer resolver at code HEAD `6de90ef83dc35cfc99c77bac8bc1e16853b1b993`, frame receipt reader in `server/services/spatial_frame_reader.py`, and the independently accepted caller-session M7 head-lock prerequisite at code HEAD `5fedfc2dca903d09e7f79a0e0a4efecb29ca39cb`. The source comparison and rejected shortcuts are in `docs/research/2026-10-05-r2-m8c-binding-create-custody-seam.md`. PostgreSQL row-order and SQLAlchemy session guidance are linked there. All new binding-authority choices below remain proposed until tests and review pass.

## First command and trusted derivation

The first command is server-internal. Its trusted caller supplies `(user_id, project_name, principal)`; its body supplies `command_id`, Shot target ID, expected exact `TargetVersionRef`, and two distinct `(frame_receipt_id, receipt_digest)` pairs. It does not accept a `ProductionBinding` body, semantic/production/asset refs, approval flag, frame view or spatial set from the client. An HTTP route, if later added, binds user/project/actor from authenticated route context before constructing this command.

The service uses the target authority in its own `AsyncSession` to lock/verify the current full screenplay admission, Scene dependency and Shot target. The repository's Shot path already checks both rows in admission → Scene → Shot order. It now returns the verified Scene on `VerifiedTargetVersion.scene` rather than requiring a second admission/Scene acquisition after Shot; the consumer resolver passes that result through unchanged (`lib/db/repositories/production_target.py`). Binding creation requires the Shot ref to equal the command's expected ref, the Scene's `location_ref` to be nonempty, and both bodies to remain approved. It derives `semantic_ref` from that exact Scene value. A missing `location_ref`, changed target head, foreign scope or malformed stored target fails before any binding version is committed.

For this first `LOCATION` role, the server derives one logical binding ID from the scoped Shot target and role using an explicitly versioned domain digest. This permits one current LOCATION head for that Shot; a later Preparation command must handle intentional core-ref replacement. It sorts the two frame candidate IDs; duplicate frame IDs or the same M7 parent artifact key fail. `asset_refs` are those two `m8f:` frame candidate IDs, in canonical order. `production_ref` is a domain-separated source-group ID over the scoped ordered frame IDs. The v1 body has `schema_version="1"`, `version=1`, `target_type="SHOT"`, `target_id` from the verified target, `role="LOCATION"`, and null variant/state refs. It carries no spatial prose or pair view labels.

## Reference claims and envelope

Each immutable claim records the source receipt ID/digest, frame candidate ID/content digest, parent artifact key/master version/candidate ID/content digest, and recipe/decoder identity from the verified receipt. `SpatialFrameReader.read_locked` must return matching current parent and verified PNG bytes; the claim is derived from its result, not echoed from command input. The two claims are ordered by frame candidate ID. The binding envelope contains scope, binding ID/version, exact v1 body digest, exact Shot target ref and Scene dependency ref, ordered claims, and null spatial-set ID/digest. The body, claim, envelope and snapshot use separate named Preparation-canonical digest domains with frozen byte vectors. No internal `object_ref` or filesystem path enters public wire or digest.

The existing `m8c_binding_snapshot_vectors.json` case at body version 2 is a synthetic illustration with shaped digests. Keep it as an adversarial propagation vector. Add separate fixed version-1 canonical vectors for the proposed byte contract, then run integration tests against actually registered targets and derived frame receipts. Fixed vector bytes alone cannot establish source authority; only a persisted read of real rows and bytes can do that.

## Transaction, replay and reads

One caller-owned PostgreSQL transaction performs: integrity-only early command lookup; scoped, unlocked receipt hints to discover the two parent artifact keys; current admission → Scene → Shot verification; scoped binding-head claim/lock; sorted distinct current M7 parent-row locks; exact frame receipt, parent projection/candidate and PNG-byte revalidation against the primitive hints; append immutable binding version; advance head with expected version zero; insert command receipt last; commit. Hints are never authority: changed receipt/parent identity after a hint fails closed. Missing binding head is claimed by insert-if-absent followed by locked reread. A losing unique-command transaction rolls back all tentative rows before it reads the winner in a fresh transaction. No nested service opens another session while these locks are held. A failed claim, race, corrupt row or byte mismatch commits no binding head/version/receipt. The two locked frames must also differ in `frame_content_digest` (amendment 2026-10-14, finding F1): spatial execution refuses a MASTER and REVERSE with the same frame content, so a binding over two identical frames could never be analyzed and is refused at creation instead.

The first create command's canonical digest covers command ID, trusted scope/actor, expected target ref and ordered exact receipt refs/digests. The result receipt binds command digest, binding ID/version/envelope digest and target ref. An exact replay verifies the stored command/result digest and current binding, target and source identities before returning the same receipt; stale or changed input fails closed. The writer never replays a historical receipt as proof of current readiness.

The proposed v1 byte contract is pinned in `tests/fixtures/r2/m8c_location_binding_v1_vectors.json` and checked by `tests/unit/r2/production_binding/test_binding_digests.py`. `m8b:` and `m8g:` are the SHA-256 hex of their respective Preparation-canonical identity and source-group envelopes. Claims include exact receipt/frame/parent identity, decoder and recipe fields; the envelope contains the two ordered claim bodies plus each claim digest, exact Scene and Shot refs, and null spatial-set fields. These vectors contain synthetic digests and establish byte compatibility only; the persistence command must validate typed shapes, current rows and source bytes before treating them as authority.

The exact snapshot reader starts from the current target/admission authority, then locks/rechecks the binding head and rehashes body, claims, envelope and the referenced current frame receipts under the sorted M7 parent locks. The snapshot digest covers sorted binding ID/version/envelope digests and exact Scene/Shot target refs. A target, parent master, frame bytes or binding head advance makes the old snapshot stale. Pure `ProductionReadinessEvaluator` can reuse verified v1 bodies, but the live readiness adapter must require a current approved pair decision before marking the spatial source READY. No generation route may rely on an unverified caller-supplied `binding_snapshot_ref`.

## Acceptance cases for this packet

- Canonical version-1 bytes and digest vectors for server-derived binding ID, production group, body, claims, envelope, command/result and snapshot; a one-byte source/target change alters the relevant digest.
- PostgreSQL create and exact replay, same-command changed-source conflict, two first writers of the same absent binding, different command IDs for the same logical binding, forced failure after staged binding work, and unique-command loser rollback.
- Forced interleavings with re-admission, target advancement and M7 master advancement; observe exact backend PIDs and blockers and assert admission → Scene → Shot → binding → sorted M7 lock order, not merely SQL table names.
- The Shot-bundle reader returns the exact Scene body used for `semantic_ref` without a new upstream lock after Shot, and rejects an absent or changed Scene dependency.
- Cross-project/user failures; missing or duplicate frame, same parent key, stale receipt/master, corrupt body/claim/envelope/receipt and changed PNG bytes all fail with no binding commit. The server-internal caller supplies trusted actor scope; an HTTP route requires its own authenticated route-context binding test before exposure.
- Snapshot reader rejects copied digest columns with altered body/claim bytes and rejects a stale binding or target head. It must distinguish a legitimate later binding version from corruption of an immutable version.
- A valid two-frame binding without an approved pair remains unavailable to live spatial readiness and promotion. Pair admission, spatial-set promotion, M7 submit integration and repository-wide release gates are separate packets.
