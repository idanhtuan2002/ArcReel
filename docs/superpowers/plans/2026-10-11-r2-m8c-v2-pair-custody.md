# M8-C V2 pair decision custody execution packet

Status: proposed implementation plan, 2026-10-11. The pure `PairDecisionV2` contract exists at `1a4b189d`; the V2 result contract and fixed vector are in the current worktree. No V2 row, production adapter, route or acceptance exists.

## Source findings and migration choice

- `m8_spatial_pair_heads.current_version` has a scoped FK to `m8_spatial_pair_decisions`, and the V1 repository revalidates the current row, command receipt and digest from `PairDecisionV1`. `PairDecisionCommandV2` cannot be stored through this path: the V1 typed command forbids extra review fields, and its digest domain is different.
- `m8_spatial_review_sessions` already holds the exact scoped session, delivery attempts and acknowledgments. `SpatialReviewRepository.consume_session` locks the session and verifies the server-computed evidence digest, but no pair writer calls it.
- Candidate: keep the existing pair decision/head/command tables and their historical V1 JSON/digests. Store the complete `PairDecisionV2` body in a new decision row at the next pair version, using its V2 command and decision digests. Add a scoped V2 custody sidecar keyed by `(user_id, project_name, pair_id, pair_version)` with non-null FK columns to that decision and to `(user_id, project_name, review_session_id)`, plus the evidence digest. The sidecar discriminates V2 rows; readers parse the body by explicit `decision_schema`, verify that V2 rows have exactly one matching sidecar and V1 rows have none, and recompute both body and custody digests. This avoids rebuilding the historical decision table while its head points back to it. This is a design candidate pending the migration and reader tests below, not an accepted authority decision.
- An alternative is to add version/evidence columns directly to `m8_spatial_pair_decisions`. It would require more migration work on SQLite because Alembic batch table replacement must account for foreign keys referring to the replaced table. Official [Alembic batch migration guidance](https://alembic.sqlalchemy.org/en/latest/batch.html) describes that behavior. The sidecar's composite FKs must use non-null child columns and explicit checks: both [PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html) and [SQLite](https://www.sqlite.org/foreignkeys.html) permit a composite FK with a null child component to escape parent matching. No external donor implementation has yet been validated for this exact authority boundary.

## Ordered gates

1. **Versioned result and storage.** The pure `PairDecisionResultV2` and its separate digest domain are implemented and pinned by a fixed vector. Revision `911c4a0e0001` and ORM implement the sidecar shape; SQLite affected migration tests and disposable PostgreSQL upgrade/downgrade/re-upgrade passed. The database success insert and foreign-session denial remain to be proven with real V2 repository writes. Keep V1 vectors byte-identical. The migration must not backfill V1 approvals or enable a route.
2. **Mixed-history repository.** Split stored V1/V2 parsing by explicit body discriminator. Reject V2 body without sidecar, V1 body with sidecar, changed inline evidence, changed sidecar digest, orphaned command receipt and nonlatest head. Preserve V1 receipt replay and current-head semantics. Test a V1→V2 sequence and V2→REJECT sequence, including corrupted row and sidecar fields.
3. **V2 decision transaction.** A separate V2 service entry point must receive the principal from an interactive JWT boundary, use the existing target→binding→pair→sorted M7 parent→grant lock order, recheck the exact two PNG streams, compare the complete session snapshot to current refs/bytes, and consume its evidence once in the same transaction as append/head advance/command receipt. V2 authorization binds the signed current grant event digest to the exact V2 command digest. Exact replay must recheck grant and sources and verify the historical inline evidence/sidecar; it must not reconsume or demand an unexpired session. Different payload under the command ID conflicts. Test forced PostgreSQL revoke, source advance, two-consumer, rollback and replay interleavings with backend PID/blocker evidence.
4. **Current reader and activation boundary.** Require the current APPROVE to be V2 with a verified sidecar and current grant/source custody before any READY or production consumer uses it; a later REJECT withdraws suitability. Keep the old V1 row readable as history. Add HTTP session/fetch/acknowledgment with interactive JWT and no-store PNG response only after external issuer-key/checkpoint custody is settled. Browser hashes returned Blob bytes, decodes both images and sends named acknowledgments. Test API-key and auth-disabled denial, role swap, missing decode/ack, expiry, stale PNG, source advance and no public static path.
5. **Acceptance.** Run affected gates on SQLite and PostgreSQL, full required checks, independent exact-HEAD review and key/checkpoint recovery drill. Production migration, grant import, APPROVE route, READY, promotion and generation remain closed until explicit acceptance.
