# Text roles fall back to other models mid-run, and a model change no longer stops a film

Decided 2026-11-13 by the main agent on the sponsor's instruction: "film projects can change models flexibly too; there must be an automatic fallback to another model on errors or exhausted quota". It builds on [ADR-0138](0138-a-story-continues-on-the-models-the-project-has-now.md) (a story keeps what was written when its routes change).

Free cloud models run out of quota mid-run (Gemini 20 requests per model per day, Groq 200k tokens per day, BytePlus and Alibaba one-time quotas), and a local model server can be down. Before this decision a failed writer stopped the story (`MODEL_UNAVAILABLE`) and a failed text task stopped its stage (`OWNER_TASK_FAILED`) until a Human acted, and any model change left the project's launch qualification stale (`LAUNCH_QUALIFICATION_CHANGED`).

1. **Fallback routes are part of the settings and the frozen policy.** A project's automation settings hold `fallbacks`: ordered models for the text roles `writer` and `script` (at most 8; never the role's own model, never twice). They are checked like any route: an enabled model of the role's media type; a cloud one needs a per-call ceiling and makes the settings non-local and paid. `RunPolicy.fallback_routes` freezes the ones still available when a run starts (one that is no longer available is left out, never refusing the run); preflight holds them to the rules of the routes they replace (`CLOUD_ROUTE_FORBIDDEN` under local-only, `UNBOUNDED_PAID_ROUTE`, and no fallback may be one of the run's reviewers: `REVIEWER_INDEPENDENCE_MISSING`). A policy without fallbacks keeps its digest.
2. **The story moves to the next writer in the same run.** When the run's story stops at `MODEL_UNAVAILABLE` (its model failed on every retry: down, quota, key, missing model) and the run's writer order (its writer, then the writer fallbacks) has a model after the story's current one, STORY reworks (`STORY_MODEL_FALLBACK`): the step settles what was spent, and the next step reroutes the story's brief onto that writer (ADR-0138 `reroute_brief`; the original basis stays, so nothing written is redone), writes it into the story task, records the move as a top-up of the step and queues the task again. The fallback routes are part of the policy the run's grant approved, so the move is authorized by the STORY step itself and the story keeps its Gate A decision. On the last writer the story stays stopped for the Showrunner. A story the run took over from an earlier run is first taken over (ADR-0138), and falls back only once its task follows this run.
3. **Text tasks fall back call by call.** A `TextGenerator` made for a project's configured model (episode planning, script generation, the project overview, style and spatial analysis, the agent's text tools) takes the project's `script` fallbacks; a generator made for an explicit model does not. A call that fails on its route (HTTP 401, 402, 403, 404, 408, 429 or 5xx anywhere in its cause chain, or a connection or timeout error) is made again on the next fallback that can do the task (one that cannot be built is skipped) and the generator stays there; an answer-level failure (bad request, schema, refusal) is raised as before. Each call is recorded in the ledger under the model that answered it. Text stages compare the project's fallbacks with the frozen ones (`MODEL_CONFIG_CHANGED`), as they already do for the script model.
4. **Saving the settings records the launch qualification again.** After a Showrunner saves the automation settings, the server records the project's launch qualification as the Showrunner's own "record launch" would (only when the real preflight blocks on nothing else) and returns the reasons it still has (`launch_reasons`), so a model change does not stop the next film run on `LAUNCH_QUALIFICATION_CHANGED`.
5. **The UI** edits the fallbacks under the writer and script models (ordered list, ceiling for a cloud model, add and remove).

Not covered, and why:
- Reviewers, the image judge and the continuity judge: a reviewer route must be qualified on its exact identity before a run uses it, so a fallback reviewer needs its own qualification first. The continuity judge already lets a storyboard pass unjudged when it gives no verdict.
- Image, video and audio: the launch profile pins them, and every cloud media adapter is `UNQUALIFIED` in production (FILM handoff finding 1), so a media fallback would need launch-profile alternatives and qualified adapters first.
- An open run's policy stays frozen. A change of primary models applies from the next run; the autopilot re-pins on save and starts it.
