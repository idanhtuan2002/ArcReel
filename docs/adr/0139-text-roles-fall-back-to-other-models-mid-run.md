# Text roles fall back to other models mid-run, and a model change no longer stops a film

Decided 2026-11-13 by the main agent on the sponsor's instruction: "film projects can change models flexibly too; there must be an automatic fallback to another model on errors or exhausted quota". It builds on [ADR-0138](0138-a-story-continues-on-the-models-the-project-has-now.md) (a story keeps what was written when its routes change).

Free cloud models run out of quota mid-run (Gemini 20 requests per model per day, Groq 200k tokens per day, BytePlus and Alibaba one-time quotas), and a local model server can be down. Before this decision a failed writer stopped the story (`MODEL_UNAVAILABLE`) and a failed text task stopped its stage (`OWNER_TASK_FAILED`) until a Human acted, and any model change left the project's launch qualification stale (`LAUNCH_QUALIFICATION_CHANGED`).

1. **Fallback models are a free list in the settings.** A project's automation settings hold `fallbacks`: ordered models for the text roles `writer` and `script` (a sanity bound of 32; never the role's own model, never twice). They are added, removed, reordered or made the role's default at any time, also while a run is open; each saved one is checked like any route (an enabled model of the role's media type; a cloud one needs a per-call ceiling and makes the settings non-local and paid). `RunPolicy.fallback_routes` records the ones available when a run starts and preflight holds them to the rules of the routes they replace (`CLOUD_ROUTE_FORBIDDEN` under local-only, `UNBOUNDED_PAID_ROUTE`, and never one of the run's reviewers: `REVIEWER_INDEPENDENCE_MISSING`); a policy without fallbacks keeps its digest. When a fallback is needed, the list is read as the settings hold it then, and each entry is held to the same rules against the run's policy (a cloud one under a local-only policy, a paid one without a ceiling, or one of the run's reviewers is passed over).
2. **The story moves to the next writer in the same run.** When the run's story stops at `MODEL_UNAVAILABLE` (its model failed on every retry: down, quota, key, missing model) and the writer order (the run's writer, then the writer fallbacks the settings list now) has a model after the story's current one, STORY reworks (`STORY_MODEL_FALLBACK`): the step settles what was spent, and the next step reroutes the story's brief onto that writer (ADR-0138 `reroute_brief`; the original basis stays, so nothing written is redone; a fallback that can no longer be built is passed over for the next), writes it into the story task, records the move as a top-up of the step and queues the task again. The fallback routes are part of the policy the run's grant approved, so the move is authorized by the STORY step itself and the story keeps its Gate A decision. On the last writer the story stays stopped for the Showrunner. A story the run took over from an earlier run is first taken over (ADR-0138), and falls back only once its task follows this run.
3. **Text tasks fall back call by call.** A `TextGenerator` made for a project's configured model (episode planning, script generation, the project overview, style and spatial analysis, the agent's text tools) takes the project's `script` fallbacks; a generator made for an explicit model does not. A call that fails on its route (HTTP 401, 402, 403, 404, 408, 429 or 5xx anywhere in its cause chain, or a connection or timeout error) is made again on the next fallback that can do the task (one that cannot be built is skipped) and the generator stays there; an answer-level failure (bad request, schema, refusal) is raised as before. Each call is recorded in the ledger under the model that answered it. The list is read when the generator is made, so an edit applies to the next text task.
4. **One default per role, and saving re-qualifies the launch.** The script model chosen in the automation settings is written as the project's text model for script work (`text_backend_complex`), so the text stages, which compare the two, run on it and a new default needs no second setting. After a Showrunner saves the automation settings, the server also records the project's launch qualification as the Showrunner's own "record launch" would (only when the real preflight blocks on nothing else) and returns the reasons it still has (`launch_reasons`), so a model change does not stop the next film run on `LAUNCH_QUALIFICATION_CHANGED`.
5. **The UI** edits the fallbacks under the writer and script models: add, remove, move up or down, a ceiling for a cloud model, and "Make default" (the fallback becomes the role's model; the model it replaces takes its place in the list).

Not covered, and why:
- Reviewers, the image judge and the continuity judge: a reviewer route must be qualified on its exact identity before a run uses it, so a fallback reviewer needs its own qualification first. The continuity judge already lets a storyboard pass unjudged when it gives no verdict.
- Image, video and audio: the launch profile pins them, and every cloud media adapter is `UNQUALIFIED` in production (FILM handoff finding 1), so a media fallback would need launch-profile alternatives and qualified adapters first.
- An open run keeps its primary models (a run is the unit a policy is approved for). A new default applies from the next run; the autopilot re-pins on save and starts it, and ADR-0138 lets that run take a stopped story over on the new default.
- Text tasks read the project's settings, not the run, so a live fallback is not re-checked against a run's local-only flag there; a Showrunner who saves a cloud fallback has made the settings non-local.

## Amended after the independent review (2026-11-13, `R2_FILM_QUALITY_REVIEW_2026-11-13.md`)

- **An open run's text tasks are held to the run** (H2, M6). The worker resolves the run a task follows (the execution guard already does) and sets its rules for the task (`lib/text_backends/fallback_rules.py`): the run's frozen script model is the one script work uses (a new default applies from the next run and never stops an open one; text stages no longer compare the project's model with the frozen one), and fallbacks are passed over when cloud under a local-only policy, cloud without a ceiling, or one of the run's reviewers. The story's writer order applies the same rules. Settings refuse a fallback that is one of the reviewers (`FALLBACK_IS_REVIEWER`).
- **Money** (H1). A priced story spends at most what the run has left: a fallback step and a take-over step reserve the run's remaining money and cap the story at it; a priced writer that does not fit is passed over.
- **Repairs** (M3). A fallback move counts as a STORY repair; past `unit_repair_limit` the story stays stopped for a Human (the run blocks, it does not fail).
- **Replays** (M1, M2). A take-over is complete only when its top-up is recorded; a fallback writes the state's top-up first, then the task's brief, then queues it, and pins the chosen brief before any write, so a replay finishes the same move.
- **Autopilot** (M4). A stopped story keeps the autopilot waiting unless the next run would take it over under the same conditions (current content safety; the book's next part, or the autopilot's own idea for a first part).
- **Launch qualification** (H4, M5). A record made stale by a model change is replaced like a missing one; the bookkeeping never fails a settings save or a films batch.
