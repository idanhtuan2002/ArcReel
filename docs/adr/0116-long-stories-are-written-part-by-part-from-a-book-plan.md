# Long stories are written part by part from a book plan and a book memory

Decided 2026-11-09 by the main agent under the sponsor's instruction to inherit the full long-novel engine of the donors (huohuo, shenbi) rather than stop at a three-chapter story. Research: [long-novel and skill gaps](../research/2026-11-09-r2-donor-long-novel-and-skill-gaps.md) §3 and §4(a), building on [donor writing capabilities](../research/2026-11-09-r2-donor-writing-capabilities.md), [ADR-0114](0114-film-episodes-are-adapted-from-the-story.md) (the story is a product, never shortened for film) and [ADR-0115](0115-stories-enter-from-ideas-text-continuations-and-variants.md) (continuation reads committed text).

Before this decision every story run wrote exactly three chapters of 7 000–11 000 syllables (`CHAPTERS = 3`), every scene received the openings of all earlier scenes, and the critic and packaging read the whole manuscript in one prompt. None of this scales to a novel, and the run's Canon plan is built from every chapter plan before the first scene is written, so a run cannot simply be made longer.

1. **A book is a sequence of parts; a part is one story run.** A brief may carry a book spec: total chapters (6–120), syllables per chapter (2 000–5 000, default 3 000; a scene holds at most 1 000 and a chapter five scenes) and chapters per part (3–6, default 5). Parts are `ceil(chapters / part_chapters)` with the remainder spread over the first parts. Narrative volumes are separate from parts: `clamp(round(chapters / 12), 1, 5)` volumes with chapter ranges computed in code (shenbi `story-architecture` budget rule; ranges never come from the model). A part run is the existing engine with its chapter count taken from the brief (`StoryLimits.chapters`), so its Canon plan, audits, approval, commit and hand-off are unchanged and bounded. A brief without a book spec is today's short story, byte for byte (the field is left out of the digest at its default).
2. **The book plan is written once, by part 1.** A `book_outline` node holds the skeleton: logline, arc, central question, ending, final image and one entry per volume (title, objective, three to five key results, turning point, up to three new characters and three new locations). Then one `book_chapters[v]` node per volume writes that volume's chapter rows, at most 8 per call (huohuo phases above 30 chapters in chunks of 15 Chinese rows; Vietnamese rows cost more output tokens). The row count is exact by schema. Each row has a core task, threads advanced, a turning point, a **chapter role** (`setup`, `advance`, `turn`, `payoff`, `climax`, `breath`), up to two hooks planted and up to two earlier hooks paid off. Hook ids (`h1`, `h2`, …) are assigned in code in plant order; a payoff names an id from an enum of the open ids and the ids the call's own plants will get, never free text, and a payoff in or before its plant's chapter is a plan problem. Code checks the plan: no three consecutive rows with one role (huohuo `chapter_role`), the last chapter is `climax` or `payoff`, every planted hook is paid within 12 chapters or carried to the ending, and no payoff precedes its plant. Failing checks are sent back for revision at most three times (huohuo gap patch, three rounds); a model review then judges the volume once, as the short outline is judged today. The book seed allows up to ten characters and eight locations; volume additions are appended to the cast in volume order, so entity keys stay stable across parts.
3. **Each part plans from the book.** A part's `outline` is a projection of its book rows (no model call). Parts after the first copy seed, bibles and book plan from the book state instead of generating them, so names, keys and style stay identical. A chapter plan receives its row (role, hooks to plant, hooks to pay, hooks overdue) and the book memory.
4. **Book memory is extracted from accepted chapters and folded in code.** After a chapter's final review a `chapter_digest[c]` node extracts a summary (at most 600 characters), up to six events, the end state of each character present (names bound to the cast; any other name must be written in the chapter as whole words, as in ADR-0115), the hooks it touched or resolved (ids from an enum) and up to three new open threads (given ids `u1`, `u2`, …). Only accepted text is read; drafts never write memory (novel-studio). At the end of a part a `part_summary` node condenses the part (at most 1 200 characters). The memory is a deterministic fold of the plan, the digests and the summaries: the last eight chapter summaries, the last six part summaries, each character's latest state, the hook ledger and the last 1 500 characters of the part. A hook is `planted`, `touched` or `resolved`, with the chapter it was last touched; it is **overdue** when untouched for eight chapters or past its planned payoff (shenbi `foreshadowing-lifecycle` max distance, huohuo plot ledger). The memory's size does not grow with the book beyond those windows (shenbi `memory-distill` bounded window).
5. **Context stays bounded.** In a book, a scene sees the earlier scenes of its own chapter and the tail of the scene just before, plus a book-memory block (the last three chapter summaries, the current state of the characters in the scene, the hooks this chapter must touch). The critic reads the part's chapter digests and its last chapter in full; only the last part is checked for a resolved ending, an earlier part for ending on its last row's turning point. Packaging reads the memory and the part's first and last chapters; selling-point quotes are still verified against the full part text in code.
6. **Book state is committed with the part and read by the next part.** Each part run produces a `book_state` node (plan and folded memory, no model call). Its digest is written into the part's quality record, which the approval binds. Hand-off writes the part's text as a new source (sorted after earlier parts, ADR-0115). The book's progress is the latest part whose run is committed and handed off. A continuation in a project whose book has parts left writes the next part from the book state instead of re-reading the text; once every part is done, a continuation behaves as in ADR-0115. Chapters are numbered across the whole book.
7. **Budgets scale with the part, not the book.** A part's call, token and wall-clock limits are computed from its chapter count (the existing `run_call_bound` plus digests and the part summary). Rewrite caps are unchanged (two chapter review cycles); huohuo's 30 rewrites per chapter are not adopted.
8. **Production runs.** A run started from an idea may name a book length; it writes part 1 and films it. A run that continues a book project writes the next part (its idea is the author's direction for that part). Starting the next part's run is a Showrunner action like any run start, because a run's automation grant is issued under an interactive session; a run that starts runs on its own would need delegated start authority, which is a separate decision.
9. **A later story of a project branches its Canon.** A project holds one `MAIN` Canon branch. The first story run commits it; every later run (a book's next part, an ADR-0115 continuation) commits a narrative branch pinned to the `MAIN` head, adding only the characters and places the head lacks and a fact naming the run. The run records that head at its first execution, so a resume keeps the same base, and the manifest names it so commit and read-back use it. Before this, a second committed story in a project stopped at commit. When two first stories race, the one that commits second is blocked `CANON_BASE_MOVED` before any commit step; a retry rebases it on the MAIN branch (its scenes are written again on that Canon, its plans kept) and offers it again.
10. **Context window is part of the manifest.** In a book a scene's context is compiled from its own chapter's earlier scenes, or from the scene just before when it opens a chapter; the manifest records that window, so commit recompiles the same pack.

Not adopted here (research §4 "What NOT to adopt"): skill-scoring gates, Chinese web-fiction timing rules and Chase Power numbers, the 15-dimension cultivation ledger, huohuo's 30-rewrite default. Audits beyond the four existing dimensions, drift detection, imported-story analysis and genre packs are later decisions.
