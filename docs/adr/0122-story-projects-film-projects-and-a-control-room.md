# Story projects, film projects and a control room for thousands of them

Decided 2026-11-09 with the sponsor: one operator manages thousands of story projects and thousands of film projects; a story project is a standalone product that may be published on its own; a film project uses a story project as its input and shows the link; the first screen is a control room; the agent panel starts folded. Builds on [ADR-0114](0114-film-episodes-are-adapted-from-the-story.md) and [ADR-0116](0116-long-stories-are-written-part-by-part-from-a-book-plan.md).

Before this decision every project was one kind (a story was written inside the project and filmed there), the lobby loaded every project with its scripts on each visit and showed them as three large cards per row under a greeting and a featured card, the operations overview asked the server once per project, and inside a project the agent panel took a third of the width by default.

1. **Two kinds of project.** `project_kind: "story"` marks a story project: written, imported, continued, varied or translated (ADR-0115 to ADR-0120), its sources are its manuscript, and its workspace shows only the story and the manuscript. A project without the field is a film project, so every existing project keeps working. A film project may name the story project it adapts (`story_project`, set at creation; the named project must be a story project). `POST /projects/{film}/story-sync` imports the story project's text into the film's sources: files it does not hold are added, identical files are skipped, a file it holds with other text is never overwritten and is reported (episodes may already be planned from it). The Showrunner of both projects may sync. Creating a film from a story imports at once; new parts of a book are pulled with the same action.
2. **A paged project index.** `GET /projects/index` returns one page (at most 200 rows) of the library, searched by title or name, filtered by kind and stage, sorted by last change, title or stage, with counts per kind; a story row carries the number of films that adapt it. Rows are cached with a signature of the project's files (`project.json`, source, scripts, storyboards, videos, adaptations) and recomputed only when it changes or after five minutes, so a page stays cheap however many projects exist. The old `GET /projects` stays for compatibility.
3. **One read of what needs the operator.** `GET /operations` returns, for the signed-in user, story runs waiting for approval or stopped, production runs waiting for review or stopped, running story and production runs, and active generation tasks per project, from the newest 500 story runs and every unfinished production run. It is read-only; each item links to where it is acted on.
4. **The control room.** The first screen is a slim top bar, a strip "Needs you" (decisions, stops, running work, folded to a line of counts and remembered per browser) and a dense table of projects with tabs All / Stories / Films, stage filter, sort and pages of 50; a film row links to the story it adapts, a story row opens on its story page. The greeting, the featured card and the card grid are removed.
5. **Room for the work.** Inside a project the agent panel starts folded (a floating button opens it; the operator's own choice is remembered), rarely used sections (formats, quality, packaging, learning from data) sit under a folded "More" group, a story project hides episodes, and a film project shows its story and an "Update" action in the sidebar.

Not adopted: a separate service for project metadata (the files stay the authority; the index is a cache), live push of operations (the strip polls every 30 s), and automatic re-sync of a film when its story changes (an edited story file can conflict with planned episodes, so the operator pulls).
