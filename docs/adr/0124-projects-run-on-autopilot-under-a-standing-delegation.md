# Projects run on autopilot under a standing delegation

Decided 2026-11-10 with the sponsor: a project has an automatic mode; a story project writes its whole story, a film project films its linked story part after part, and "make films for finished stories" creates one film project per story in order; no limit beyond each run's own caps. Research: [workspace grants and autopilot](../research/2026-11-10-r2-workspace-grants-and-autopilot.md) §3, option B3. Amends [ADR-0116](0116-long-stories-are-written-part-by-part-from-a-book-plan.md) §8 and [ADR-0122](0122-story-projects-film-projects-and-a-control-room.md) ("not adopted": automatic re-sync), extends the lock order of [ADR-0111](0111-autonomous-production-run-authority.md).

1. **The Showrunner's decision is recorded.** Turning autopilot on (an interactive Showrunner, with a current project or workspace grant, ADR-0123) appends a delegation version: project, kind (story or film), issuer, the parent grant chain with its sequence and digest, the policy digest frozen at enable, story parameters (book length, the first idea, the continuation direction) or film parameters (episodes per run), the command id and a digest of all of it. Turning it off appends a disabled version; it stops future starts (Pause stops the run in progress). Records are append-only.
2. **Starts without a click, bound to that decision.** A scheduler in the app process (the pattern of the production scheduler: database scan, lease, `SKIP LOCKED`) starts production runs through narrowly typed custodian entries that take a locked, enabled delegation instead of a session token. They require the delegation's digest, issuer, policy and the parent chain's exact sequence and digest to still hold, so a revoked or re-issued parent, a disabled delegation or a moved policy halts the project. Child grants record the chain they were bound to and expire with their parent rather than after 24 hours. Gate A and story approvals are unchanged: production runs already decide them under the run's grant with automatic provenance (ADR-0111).
3. **A story project runs story-only runs.** `RunCommand.end_stage = "HANDOFF"` (left out of the stored command at its default) ends a run after the story is committed and handed off. Part 1 starts from the idea and book length; each next part is a continuation of the book (ADR-0116), started only when the previous autopilot run succeeded and no other story run of the project is unfinished.
4. **A film project follows its story.** When the linked story has handed off more parts than the film holds and the film has no active run, the scheduler syncs the story (ADR-0122) and starts a film run from the project's sources; a sync conflict halts the project instead of overwriting.
5. **Idempotent and stoppable.** A start's command id is derived from the delegation digest and the part ordinal, so a crash replays the same run; one active run per project is enforced by the existing unique index. Any outcome other than success (blocked, waiting for review, failed, cancelled) halts the project's autopilot and shows it under "Needs you"; when the operator resolves it and the run succeeds, the next scan continues.
6. **Films for finished stories.** An interactive batch command walks the story projects whose story is finished and that no film adapts, in creation order, creates one film per story (named from the story, linked, synced) and turns its autopilot on, bound to the batch command; a restart resumes from the batch cursor.

Risk accepted by the sponsor: no spending cap beyond each run's caps; many projects on autopilot can spend in parallel, paced only by the scheduler batch and resource admission. Renewing the workspace grant halts every autopilot until a bulk re-enable.

Amended after review (2026-11-10): a story start command names the part it writes (`…:p<n>`), and the autopilot halts (`PART_NOT_RECORDED`) when the last part it wrote does not show in the book, instead of paying for it again; it never writes a book over a project's story that is not a book (`STORY_WITHOUT_BOOK`); it waits while another story run of the project is unfinished. A reader's view of the autopilot writes nothing (the film's story is synced only before a start). A command replays the version it recorded, so a retried old enable never re-enables. A story-only run skips the film-only preflight reasons (media routes, voice, image judge, launch qualification, quality profile) but keeps disk and GPU room. Films made by the batch need their own launch qualification and quality profile before their runs pass preflight; the autopilot shows the refusal.
