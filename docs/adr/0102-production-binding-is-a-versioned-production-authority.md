# ProductionBinding has one versioned authority and carries an exact spatial constraint reference

ADR-0095 stopped M8-C promotion because R2 has a `ProductionBinding` contract but no persistent authority. This ADR chooses the full promotion path over a candidate-only amendment. It is a design candidate until the review and acceptance gates below pass. It does not release the stopped M8-C implementation.

## Evidence and decision boundary

The [binding research](../research/2026-09-30-r2-m8c-production-binding-authority.md) and [consumer comparison](../research/2026-09-30-r2-m8c-consumer-options.md) establish that current bindings and `SceneSpec`/`ShotSpec` are fixture or pure values in the inspected R2 runtime, M8-A refuses the binding target, and no live generation path reads spatial constraints. The bounded searches cover `r2`, `lib`, and `server` at the stated worktree HEAD; they do not prove global absence. The graph index is for another checkout and predates these M8 files.

The accepted M8 design assigns `SpatialCandidate` to `PRODUCTION_BINDING`. A candidate-only packet would leave C2's promotion and M8-D's dependency unsatisfied. A binding store with no typed spatial value or consumer would accept data without a production effect. The selected design supplies all three, in dependency order: target and binding authority, spatial representation and read path, then M8 promotion. This is an inference and design choice from the cited evidence, not a claim that those components already exist.

## Decision

1. **Production Preparation owns binding writes.** A project-scoped PostgreSQL head keyed by `(user_id, project_name, binding_id)` points to immutable binding versions. Each version stores a v1 `ProductionBinding` body, its canonical digest, optional exact spatial constraint ID and digest, actor, command key and provenance. The v1 schema and existing fixture serialization stay intact; a spatial update increments the body's `version` and the version envelope carries the new spatial reference. A single writer performs expected-version CAS, command replay validation, append and head advance in one transaction. M8 calls this authority through a narrow port inside its promotion transaction; Canvas, M7 master slots, asset rows and manifests are never independent binding writers.
2. **Targets have checked identities.** A production binding may reference only an exact, approved, project-scoped `SceneSpec` or `ShotSpec` version registered by Production Preparation. Since the inspected host has no such persistent registry, the first authority packet includes an explicit target registration and exact-version reader. The initial supported family is Take-derived targets: registration must re-read the exact current screenplay admission through a transaction-bound version of `ApprovedScreenplayReader`, deterministically derive the target with `TakeDirectorAdapter`, and bind its resulting content digest and upstream admission decision. The registry owns a separate monotonic immutable version/head because the adapter currently stamps every derived body `version=1`; a new admitted screenplay can change content under the same target ID. Other Director families require their own exact upstream authority proof before registration. An opaque client `target_id`, self-asserted approval field or Golden fixture cannot stand in for this check. Binding creation requires a separate Production Preparation command with typed semantic, production, role and asset identities; M8 spatial promotion can only update an existing `LOCATION` binding and cannot create one or replace its core refs. An approved reference claim needs an exact content digest and custody proof from its owning authority. The mutable global asset row alone is insufficient.
3. **Spatial evidence stays separate from production facts.** A typed immutable `SpatialConstraintSet` selects assertion IDs from one exact `SpatialCandidate` revision. It records source media authority identity/digest, source spans, observed view, semantic relation, seam and direction locks, duplicate exclusions, normalizer version and provenance. A production constraint is derived only from explicitly selected `VISIBLE` assertions whose source identity and spans resolve exactly. `INFERRED`, `GAP`, unknown source, and conflicting assertions remain in the candidate and preview as evidence; they cannot be promoted as facts. The original candidate revision is never rewritten. No donor free text is accepted as a binding identity.
4. **One exact snapshot drives readers and a reachable generation entrypoint.** The binding authority returns a snapshot ID over ordered binding IDs, versions and envelope digests. Readiness and content fingerprinting use that same snapshot; a changed binding head invalidates stale readiness. A typed spatial resolver reads the constraint set through the exact binding version and passes its permitted constraints into R2 `PromptPlanner`/compiler output. Before M8-C acceptance, one application generation entrypoint must resolve that exact snapshot, recheck readiness currentness itself, compile the visible constraints, bridge the M4 method-origin request to M7's host-task origin, and commit the currentness proof with the M7 `PLANNED` attempt before external submit. The caller-supplied `readiness_is_current` boolean is not authority. Golden-script prompt output alone does not meet this gate. The selected donor consumer is only a behavior comparison; R2 must test its own prompt effect on the same fixture and preserve visible/inferred/gap boundaries.
5. **Promotion is preview-bound and atomic.** The M8 preview carries the exact candidate revision/digest, selected assertion IDs, typed constraint-set proposal/digest, existing binding ID/version/envelope digest, target version/digest, source media digests, actor scope, impact and expiry. Authorization names its preview digest. Promotion locks the M8 command key, candidate head, preview, binding head, upstream admission head, scene/shot registry heads, sorted M7 master heads and sorted candidate objects in that order through one PostgreSQL session. It revalidates all bound identities and selected evidence, then writes the constraint set, binding version, authorization, promotion receipt and command receipt in one transaction. Exact replay returns the stored receipt; changed body with the same command key fails. Stale, corrupt, unauthorized or expired inputs commit none of those rows.

## Interface consequences

- A public caller cannot append a `SpatialCandidate` through M8-A's generic revision endpoint. Only a server-owned completion service may append one after a verified successful M7 execution, exact raw-response/source digests and schema-first normalization. Existing user-authored Canvas/Format revision behavior is a separate arm.
- The current M8 preview request has only candidate, revision, target and command ID. A separate typed spatial-preview request and persisted proposal must bind the selected assertions and binding/source identities. The untyped `impact` field cannot carry a client-authored binding body. Existing artifact-slot preview/receipt bytes and digests remain valid; the spatial target gets a separately versioned wire and persistence arm.
- The production snapshot and spatial resolver are new contracts. Existing Golden fixtures remain offline values unless explicitly registered; no backfill silently turns them into production authority.
- A binding version may attach a spatial constraint while preserving the v1 field schema. Its version changes; snapshot fingerprints must include the envelope digest so a spatial change cannot masquerade as the previous production input.
- The initial spatial source family is two immutable frames derived from two distinct exact, approved M7 episode-video master heads. The live Gate C approval path and projection are video-specific; an image-master approval route is not evidenced in the inspected source. Each frame needs a server-owned immutable derivation receipt binding parent identity, extraction recipe/version, frame object/digest and command replay; the existing candidate-object row alone cannot prove that lineage. A separate authorized `SpatialPairAdmission` must bind both exact frames to the same target location and record reviewed front/reverse roles and camera relation. Two unrelated approved videos cannot form a promotable pair. `DatabaseMasterResolver` checks each current parent master and its legacy projection; the candidate-object store and derivation receipt verify both parent and frame bytes. Execution rehashes the frame bytes before use. A standalone image or candidate object without approved-parent and pair lineage is unavailable until its own custody design passes independent review. Public wire/digests carry opaque frame IDs and digests, never internal object paths. Asset URLs and mutable asset rows are not sufficient. The [source comparison](../research/2026-09-30-r2-m8c-spatial-source-custody.md) records the evidence and remaining fixture gate.

## Alternatives rejected

- **Candidate-only M8-C and roadmap amendment:** safe as an interim milestone but does not satisfy the accepted C2 promotion target or M8-D release dependency. It remains the behavior while this authority is absent, not the completion criterion.
- **Put spatial prose in `ProductionBinding.production_ref` or `asset_refs`:** destroys the identity meaning of those fields and loses typed seam/gap provenance.
- **Promote through an M7 artifact slot:** a master artifact is not a semantic-to-production binding and ADR-0095 already rejects that substitution.
- **Create a binding from donor JSON:** generic spatial relations lack the typed target, semantic, production and approved asset identities. This would turn inference into authority.
- **Extend the v1 binding body directly:** adds new serialized fields to a frozen contract and changes existing fixture/content hashes without a migration need. A version envelope gives exact spatial identity while preserving the v1 schema.

## Required acceptance sequence

1. Review and accept this ADR and a concrete design spec for Take target registration from the current screenplay admission, two M7 approved source masters, binding CAS, immutable constraint storage, digest domains, authorization, wire versioning and transaction order. Confirm that the new registry records derived targets without becoming a parallel approval authority.
2. Implement and independently accept target/binding authority with corruption, stale-head, cross-project, replay, rollback and snapshot-reader tests. Then implement the typed spatial resolver and a reachable application generation entrypoint that rechecks snapshot currentness and carries its identity into the M7 request. Same-fixture prompt proof and a submit-boundary integration test are required. The authority must be useful and checked before M8 writes to it.
3. Execute M8-C C1 candidate normalization and C2 bounded execution independently of the blocked promotion step. Only after step 2 may C2 add preview/authorization/promotion. Reseal donor differential parity, exact integrated HEAD, required skips and independent review under R2-DEC-031. M8-D starts only after the complete M8-C packet is accepted.

Until these gates pass, `PRODUCTION_BINDING` preview/promotion continues to fail closed with `M8_REQUIRED_EVIDENCE_MISSING` at the packet level and `m8_promotion_target_unavailable` at the API boundary. No candidate-only result is reported as M8-C acceptance.
