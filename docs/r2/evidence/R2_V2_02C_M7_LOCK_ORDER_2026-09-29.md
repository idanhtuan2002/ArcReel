# V2-02c: M7 promotion takes the authority row lock before appending history

## Finding

Source: the independent Codex review of M8-A (`dc13cc93..21821568`), finding 2.

`AtomicPromotionService.promote` appended the `master_head_versions` row and only then ran the
pointer CAS (`advance_head`), whose `UPDATE` takes the `master_authorities` row lock.
`serialized_artifacts` (Gate C, Gate D) and the M8 slot authority take that row lock first.
A row-lock holder and an unserialized promotion of the same slot could therefore each hold what the
other waits for:

- the unserialized promotion holds the uncommitted history row's unique key and waits on the row lock;
- the holder then appends the same next version and waits on that unique key.

In the codebase today, the unserialized writer is `scripts/r2/backfill_master_authority.py`, which
writes `EPISODE_VIDEO` keys, the same keys Gate C serializes.

## Lock model (one order for every same-slot writer)

`master_authorities` row → `master_head_versions` row. The promotion calls `advance_head` first. Its
compare-and-set `UPDATE` takes the row lock, or waits for the holder and then matches no row
(`MasterHeadConflictError`). Only after that does it append the history row. There is no foreign key
between the two tables, and both writes commit in one transaction.
