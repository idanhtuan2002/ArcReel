# M8-C target registration transaction seam — source checkpoint

Status: bounded source finding for the next authority gate, not an accepted implementation design. Inspected code HEAD `88e568f242994a21049209adccc2bea75f351be4` on `impl/r2-m8c-frame-receipts`. The repository knowledge graph generation predates this worktree's new modules, so the cited sources were read directly.

## Observed source behavior

- `r2/adaptation/screenplay_reader.py` implements `ApprovedScreenplayReader.get_exact_admitted` through its own `AdaptationUnitOfWorkFactory`. It checks the exact admission row, locks the screenplay admission head, folds its decisions, compares the effective decision and selected artifact, and verifies screenplay content hash before returning the screenplay.
- `lib/db/adaptation_uow.py` creates a fresh `AsyncSession` per reader call and rolls back and closes that transaction on exit. `lib/db/repositories/adaptation.py` takes a PostgreSQL row lock in `prepare_or_lock_head`.
- `r2/production_intelligence/take_director.py` accepts a structural `ApprovedScreenplayReaderPort`; `TakeDirectorAdapter.direct` calls it once and derives scene and shot values. Its first Take bodies stamp `version=1`. The existing two-admission probe in `tests/integration/r2/adaptation/test_screenplay_admission.py` confirms a changed admitted screenplay can retain the same target ID and body version while changing the target content.
- ADR-0102 and `docs/superpowers/specs/2026-09-30-r2-m8c-binding-authority-design.md` require target registration to re-read current admission and append/advance target registry authority in one transaction. Calling the existing reader and then writing the target in a separate session would leave an admission-advance interval between check and commit.
- `r2/contracts/adaptation.py` defines `AdmittedScreenplayRef` with `screenplay_ref`, `admission_ref` and `profile_ref`. `lib/db/repositories/adaptation.py` reconstructs all three from `adaptation_screenplay_admissions`, but the existing reader method accepts only the first two and `TakeDirectorAdapter.direct` passes only those two. The future target-registration command must compare the requested full ref with that stored projection in its bound transaction; otherwise a forged profile ref could be recorded as target provenance. This is a source-confirmed gap in the proposed registration seam, not evidence that the current M6 reader promises to authenticate a profile it never accepts.

## Next design check

Design a transaction-bound screenplay reader port using the same `AsyncSession` and existing `AdaptationRepository` checks, while preserving the public `ApprovedScreenplayReader` path for its current callers. Pass that port into the existing `TakeDirectorAdapter` so target derivation reuses its behavior. Define and verify the cross-family lock order for admission head, target head and binding head before schema or writer implementation. Prove with a forced PostgreSQL interleaving that admission advance cannot slip between target proof and registry commit; also test exact replay and two admissions with the same target ID but different canonical digests. This is an implementation direction to evaluate, not an accepted authority decision.

## Reuse options and lock-order finding

1. **Preferred seam to test:** extract the current exact-admission checks into a repository-level function that accepts an `AdaptationRepositoryPort`. The existing `ApprovedScreenplayReader` calls it within its own UoW; a new transaction-bound port calls it with `AdaptationRepository(the_registration_session)` and does not commit or close that session. Bind the new port to the command's full `AdmittedScreenplayRef` and require its profile ref to equal the stored admission projection. `TakeDirectorAdapter` already accepts the reader protocol, so both paths use the same derivation and validation behavior. This requires an exact integration test proving that the registered target still holds the admission-head lock through its registry append.
2. Calling the existing reader before a separate target transaction leaves a time-of-check/time-of-use gap. Calling it twice and rechecking in the writer could close the gap only by reproducing all admission and fold checks; that duplication makes future drift likely. These are rejected candidates for the authority writer, subject to the design review.

The previous promotion draft placed the binding head **before** the admission and target heads. Registration naturally needs admission then target; a separate binding-create command that locks target then binding would invert that previous promotion order. No binding-create writer exists yet in the inspected source, so this is a prospective deadlock risk, not an observed failure. Before accepting the revised target/binding spec, verify the actual SQL lock acquisition order with forced PostgreSQL interleavings. Do not infer safety from a diagram alone or add a second session while holding these locks.

PostgreSQL 16's [explicit-locking documentation](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-DEADLOCKS) says cross-object locks should be acquired in a consistent order to avoid deadlocks. SQLAlchemy's [session guidance](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks) treats `AsyncSession` as a mutable transaction used sequentially by one task, not concurrently shared among tasks. Those are primary-source constraints; they do not prove that this project's proposed order is sufficient.

The ADR and design-spec draft now propose admission → scene target → shot target → binding → pair → sorted M7 masters → sorted candidate/frame rows after each command's existing prefix. That order is an inference from the current writer dependencies, not an accepted migration or verified lock protocol. The target-registration writer uses admission and target; binding creation/update adds binding; pair admission and generation planning extend the same sequence. The M8 spatial arm retains the accepted command → candidate head → preview prefix before entering that common sequence. Implementation must trace actual SQL, including row creation and FK checks, and demonstrate the cross-writer interleavings before the design gate accepts the order.

Fresh focused checks at design HEAD `efe5be60593cde98806a2df4d5e308cfd82ccab0` returned **20 passed, 1 PostgreSQL-specific skipped** for the persisted admission/Take test file on SQLite, and **2 passed** for the proposed binding-snapshot vector tests. The latter emitted one unrelated SQLite expression-index reflection warning. These tests verify existing derivation and canonical bytes; they do not exercise a target registry, binding writer or cross-writer lock order. The binding snapshot fixture currently uses shaped target digests rather than a registered target version. A target-registry vector and real registry-backed snapshot test remain part of the authority gate.

## Target digest domain check

`SceneSpec.duration_target` and `ShotSpecV2.target_duration` are floats. The existing Production Preparation `r2.contracts.fingerprints.canonical_json_bytes` and M8 `r2.advanced_creative.digests.canonical_json_bytes` do not emit identical numeric bytes: a direct local probe on `{"duration_target": 1e-7}` returned `{"duration_target":1e-07}` from Preparation and `{"duration_target":0.0000001}` from M8. Both are valid JSON representations of the same number, but their SHA-256 digests differ. The previous Take-target probe used the M8 helper for **illustrative body digests**; those values are not yet target-registry authority digests.

For the proposed registry, reuse the Production Preparation canonical helper on `model_dump(mode="json")` with a new versioned target-body domain and a separate target-version domain that binds scope, registry version, full stored `AdmittedScreenplayRef`, Take derivation version and the shot's exact scene-registry dependency. Do not import M8's digest helper into Production Preparation or silently compare digests from the two domains. Before acceptance, freeze exact bytes for a small fractional duration and both real admission versions; validate the domain and stored-body digest on every authority read. The existing binding snapshot vector's shaped target digest must be replaced by a registry-backed digest in an integration test. This is a design recommendation pending the target-registry packet review, not a live contract.

The proposed `tests/fixtures/r2/m8c_target_registry_vectors.json` now records two synthetic Take screenplay inputs and eight exact target-body/version envelopes. `tests/unit/r2/advanced_creative/test_m8c_target_registry_vectors.py` verifies fixed Preparation canonical bytes and SHA-256 values, model-valid Scene/Shot bodies, full admission refs, scene dependency, registry versions 1→2 while the embedded target body version stays 1, and a same-fixture Take derivation. The new tests first failed because the fixture was absent, then returned **3 passed** with one SQLite reflection warning after fixture creation. Ruff check, format and test audit passed after import/format correction. The screenplay content hashes and admission decisions are synthetic values for byte design; this does not prove a persisted admission, a target registry writer, cross-writer locking or a registry-backed binding snapshot. `r2-take-director-v1` is a proposed derivation-version label and must be pinned by the eventual producer before these version envelopes become authority.

## Registration caller boundary

The current M8 router in `server/routers/advanced_creative.py` takes `CurrentUser`, uses `user.id` for DB scope and the project from the URL path, and does not accept a body-supplied user ID. The screenplay admission route in `server/routers/gates.py` similarly takes `CurrentUser` and requires `command.project_name` to equal the URL path before invoking authority with `user.sub`. The target registry packet should keep its first writer server-internal, taking trusted `(user_id, project_name, principal)` from its caller rather than an arbitrary candidate payload. If an HTTP route is added, it must bind route scope and authenticated actor before constructing the command; the registry itself must scope every lookup, command receipt, target head and version by user/project. The inspected routes do not establish a separate project-membership authority for this packet, so claiming such a check would require new source evidence or an explicit policy design. Target registration records derived evidence; it does not approve a target independently of the upstream screenplay admission.

## First target-registry execution packet — 2026-10-05

The proposed spec now fixes scoped head/version/command tables, a full Take bundle writer, `SCENE`-typed Shot dependency and command/result digest domains. `docs/superpowers/plans/2026-10-05-r2-m8c-take-target-registry.md` breaks the prerequisite into schema, verified digest/read, atomic registration and PostgreSQL interleaving gates. The target-vector test now asserts the explicit `SCENE` dependency type; its fixed Shot version bytes and digests were updated. The affected persisted-admission, Take, target-vector and binding-vector selection returned **35 passed, 1 PostgreSQL-specific skipped** on SQLite after this update.

Self-review found that an absent command receipt cannot be row-locked. The spec therefore checks an existing receipt early but inserts the unique scoped receipt last. A racing same-ID writer rolls back its entire tentative bundle on unique conflict and then verifies the committed winner in a new transaction. Exact replay also requires the current admission and referenced current target heads; a historical receipt is not a fresh success. The proposed PostgreSQL tests must force same-ID races across different bundles as well as same-target races. This protocol is still a proposal: no target registry tables, writer or replay tests exist yet, and no PostgreSQL lock proof or independent design acceptance is claimed.

The first command/result fixture extension adds four exact envelopes to `m8c_target_registry_vectors.json`: two full-admission commands and two results containing their command digest plus ordered Scene/Shot target-version refs. The test first failed with the four absent cases, then returned **4 passed** after freezing the Preparation canonical bytes and SHA-256 digests. The two admission variants have distinct command and result digests. These are synthetic proposed receipt bytes; neither SQL replay nor same-ID concurrency has been implemented.
