## Required evidence and current stores

The accepted M8 spec §8 requires a bounded M7 execution and retention of the raw response digest, model/route fingerprint, prompt/schema version, source media digests and normalization version. It creates no revision on malformed output, missing source, provider failure or normalization mismatch (`docs/superpowers/specs/2026-09-13-r2-m8-canvas-learning-multiformat-design.md:646-658`). The C1 public append guard now rejects caller-authored spatial revisions (`r2/advanced_creative/exploration.py:179-200`), but there is no server-owned completion path in the inspected C1 worktree.

`AttemptSnapshot` retains execution ID, task ID, request digest, route, provider job ID, state/version and timestamps, but has no raw response body or object identity (`r2/contracts/host_hardening.py:158-179`). Its database row has the same state/request/route focus (`lib/db/models/host_hardening.py:50-107`). A successful attempt is therefore necessary execution evidence, not sufficient spatial-response custody.

The generic task row has `result_json` (`lib/db/models/task.py:12-31`), written by `mark_succeeded` in a status transition (`lib/db/repositories/task_repo.py:662-684`). That row carries no content digest or immutable raw-object receipt. A completion service cannot treat it alone as the exact response bytes required by M8 §8. M7 candidate objects have immutable media identity and digest, but their current preparation contract invokes a `media_probe` and publishes with `os.replace` (`lib/candidate_store.py:77-175`). The separate frame-custody research has already found a no-overwrite race at that publication seam. Reusing this media authority for JSON without a reviewed object kind, integrity rule and no-overwrite fix would blur its boundary.

The current C1 `SpatialPayload` stores assertions, locks, warnings, optional `execution_id` and `normalizer_version` (`r2/contracts/advanced_creative.py:320-339`). Source spans carry frame digest/view, but neither this payload nor `ExplorationRevision.lineage` stores raw-response identity, prompt/schema versions, model fingerprint or an ordered two-frame derivation-receipt set (`r2/contracts/advanced_creative.py:148-198`). `ExplorationRepository.append_revision` validates the supplied payload digest and stages revision plus command receipt (`lib/db/repositories/advanced_creative.py:232-325`); it does not attach execution evidence. These are design gaps in the dirty C1 candidate, not evidence that the accepted M8 spec was relaxed.

## Proposed authority contract

Use one immutable **spatial execution evidence receipt** as the source of completion. Its canonical body should bind the scoped terminal successful execution ID and request/route fingerprint; raw response and overlap-response object IDs, byte digests and schema versions; exact prompt version; ordered MASTER/REVERSE frame derivation receipt IDs and digests; and normalizer version. The object reader must rehash raw bytes and source frames at completion. A receipt digest should be bound into the spatial candidate payload (or an equally strict same-transaction revision link) so an otherwise identical candidate cannot be replayed against different raw/model/source evidence. Avoid a circular digest: compute the input receipt first, then the payload digest over the receipt link and normalized result.

The proposed completion service should lock/recheck the scoped attempt and source authority in a defined order, validate the raw schema, normalize from rehashed bytes, and stage receipt plus revision plus command receipt in one database transaction. Same execution, raw bytes, source identities and command is an exact replay; changed evidence under the same execution or command is a conflict. Failed/cancelled/unknown attempt, changed source head, corrupted object, invalid schema or normalization error yields no revision. The generic client append route remains closed to spatial payloads.

Two designs remain open: put the full receipt body inside a versioned `SpatialPayload`, or store an immutable receipt row and bind only its digest in the payload. The latter keeps bulky execution evidence outside candidate content but needs a scoped foreign key, atomic insertion/read and rehash at every authority boundary. Neither design is selected until the frame-receipt schema and M7 raw-result publication seam are tested under the same fixture. No migration, provider call, execution adapter or completion service is implemented by this note.

The proposed canonical body is fixed in `tests/fixtures/r2/m8c_spatial_completion_evidence_vector.json`. It uses the existing proposed MASTER/REVERSE frame receipt IDs and digests from `m8c_source_digest_vectors.json`; it additionally binds scoped execution/task IDs, terminal state/version, request and route digests, provider job ID, prompt digest/version, raw and overlap response object IDs/byte digests/schema versions, normalizer version and ordered frame content digests. The test checks exact canonical bytes, SHA-256, cross-fixture frame links and digest changes when raw/overlap bytes, request/route/prompt or frame order/receipt change. The focused vector file passed **2 tests** under isolated SQLite; Ruff check/format, basedpyright (**0 errors, 0 warnings**) and test audit (**0 violations**) passed. These synthetic IDs/digests specify a proposed identity shape only; no source authority, provider result or database row is verified by the vector.

In the earlier source fixture, `frame_receipt_id` currently has the same bytes as `frame_candidate_id`; no separate persisted frame-receipt row or identity exists. The implementation design must state whether that alias is intentional and enforce a scoped receipt lookup plus digest verification, or assign a distinct receipt ID before migrating. The completion vector does not resolve this authority choice.
