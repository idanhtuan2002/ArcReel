# M8-C first video-route fixture comparison

Status: **provisional offline fixture choice, not a production provider decision or M8-C acceptance**. Source inspected at design HEADs `ef82f52295a886cc2b6d01df28ad5477435ad874` and `8c545857cd3446b4738e9ffc36361d01b496c5c3`. No paid call was made.

## Required first-fixture behavior

The fixture needs two ordered, approved front/reverse frame objects, a Shot with spatial constraints in its compiled prompt, an exact M7 submit tuple, and a provider payload that can be constructed once from pinned bytes and submitted unchanged. It must reject any M4 control or reference that the selected backend cannot represent. A provider accepting two images does not by itself prove that it will obey spatial relations; the gate needs a same-fixture prompt/byte comparison and later product-quality evidence.

## Fixture direction

Use Wan `wan2.7-r2v` as the first **offline** two-view execution-profile fixture, limited to a Shot with **no required audio control** and no more than five verified references. This choice has the strongest directly readable current API-to-backend shape evidence of the inspected candidates. Derive a real versioned M4 capability descriptor/profile for its actual M7 route; map selected capability ID separately from backend model ID; capture front/reverse media bytes in fixed order; include provider-payload digest and route in the host request; and test changed source bytes, order, prompt image-number binding, unsupported audio/identity control, over-limit reference rejection, and active-task snapshot conflict before any provider submit. If the source or prompt contract cannot represent a required semantic, fail admission. Kling remains a local-backend comparison until its model/endpoint/schema compatibility is independently established. Neither fixture is authorization for a paid/production route.

## Proposed first execution-profile boundary

The first profile is a **draft fixture contract**: a selected M4 capability ID and descriptor version map to `provider_id=dashscope`, `provider_model_id=backend_model_id=wan2.7-r2v`, `endpoint_id=video-synthesis`, `adapter_version=host-video-v1` and capability profile `dashscope-video-synthesis@host-video-v1`. The M4 capability ID remains a separate identity. The input has exactly two ordered frame receipts for one admitted location pair; the prompt formatter must bind front to `Image 1` and reverse to `Image 2`, matching the official API's media ordering rule. The fixture uses a five-second output, an explicitly chosen 720P resolution, no first/end frame, no seed, and no required audio control. These values are inputs to validate, not defaults inferred from mutable backend settings.

The profile refuses a Shot requiring `silent`, `narration`, `dialogue`, unsupported identity lock, extra media, non-integer duration or a prompt beyond the selected route's limit until each has an exact mapping. In particular, the repo's `ALWAYS_ON` audio declaration cannot satisfy `silent`, while generated audio cannot establish exact narration text. Admission must check these before queueing; the backend's over-limit truncation must never be reached by this route. The draft still lacks an implemented M4 descriptor, deterministic semantic-to-prompt formatter, immutable execution projection, and same-fixture prompt test. Those are the next consumer design/implementation proof, followed by route-to-M7 planning under currentness and independent review.

## Spatial prompt projection boundary

Source inspection at `549125a6` found that `PromptPlanner.build` accepts only a Shot, method decision and resolved visual identity. It copies `shot.framing` into `composition_intent`; neither that method nor `PromptPlan` has a typed spatial-set or binding-snapshot field (`r2/production_intelligence/prompting.py:42-73`, `r2/contracts/execution.py:48-74`). `DefaultPromptCompiler` then copies generic semantic fields into a provider-neutral JSON payload (`r2/production_intelligence/prompting.py:135-167`). This explains why the admitted Take probe proves an available Shot and audio boundary but cannot prove any spatial effect. The repository graph search returned no matching R2 symbols and coverage marked the planner and advanced-creative contract as missing freshness, so these observations come from the exact design-worktree source.

The proposed first formatter input is an **exact resolved binding snapshot**, its two ordered `MASTER`/`REVERSE` frame receipts, and only the selected `VISIBLE` typed constraints from its immutable spatial set. It should emit a versioned semantic projection containing the Shot's existing subject, composition, camera and timing; a deterministic `Image 1` front / `Image 2` reverse role map; and one stable clause per supported `PRESERVE_ON_WALL` or `SHARED_SIDE_ANCHOR` constraint. Clauses must carry subject, relation and server-stamped wall without promoting `INFERRED`/`GAP` warnings to scene facts. The Wan-specific formatter may then render that projection into the exact prompt syntax of the selected execution profile. Source spans and assertion IDs stay in the captured provenance and digest even if the provider prompt omits coordinates. This is a design candidate, not current behavior.

The same-fixture acceptance case should compare the admitted Shot with and without one eligible constraint: semantic projection, provider prompt, compiled request and host request digests must change while the two image bytes and their order remain fixed. A separate reversal case must change image order, role mapping and payload digest together; swapping bytes without the prompt roles must fail admission. An `INFERRED`/`GAP`-only change may alter evidence/snapshot digest but must not add a positive spatial clause. Unsupported relation, ambiguous wall, missing object-level source span or absent pair admission fails before task creation. These tests require the still-unimplemented typed resolver and execution projection; a prose-only assertion in today's generic `PromptPlan` would not establish the authority chain.

## M4 descriptor registration boundary

`CapabilityDescriptor` has no backend model or M7 endpoint field; it records `capability_id`, `adapter_id`, `provider_id`, execution type, features, limits, source and version (`r2/contracts/capabilities.py:25-39`). The source search over `r2/**/*.py` found descriptor construction only in `r2/production_intelligence/fixture_loader.py:179-190`, where the Golden fixture uses synthetic adapter IDs and `local`/`cloud` providers. `CapabilityRegistry` accepts a supplied sequence of descriptors and observations; it does not itself load a live catalog (`r2/production_intelligence/capability_registry.py:175-196`). The inspected host route inventory separately contains `dashscope-video-synthesis@host-video-v1` (`r2/host_hardening/route_inventory.py:50`). These scoped findings mean the hand-built Wan M4 descriptor from the earlier probe is not a registered production capability.

The first implementation fixture must therefore explicitly create a versioned M4 descriptor with `VIDEO_OUTPUT` and a matching observation, plus a separate reviewed execution-profile record mapping its exact capability ID and descriptor version to the host route/model/endpoint. A stale or unknown observation must remain ineligible under the M4 matcher; route presence alone does not supply availability, credential, health or quota evidence. The fixture must prove that changing either descriptor version or host profile version rejects before queue admission. This registration and mapping are still proposed; no live catalog or activation was added.
