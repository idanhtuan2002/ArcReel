# M8-C first video-route fixture comparison

Status: **provisional offline fixture choice, not a production provider decision or M8-C acceptance**. Source inspected at design HEADs `ef82f52295a886cc2b6d01df28ad5477435ad874` and `8c545857cd3446b4738e9ffc36361d01b496c5c3`. No paid call was made.

## Required first-fixture behavior

The fixture needs two ordered, approved front/reverse frame objects, a Shot with spatial constraints in its compiled prompt, an exact M7 submit tuple, and a provider payload that can be constructed once from pinned bytes and submitted unchanged. It must reject any M4 control or reference that the selected backend cannot represent. A provider accepting two images does not by itself prove that it will obey spatial relations; the gate needs a same-fixture prompt/byte comparison and later product-quality evidence.

## Fixture direction

Use the dated Wan `wan2.7-r2v-2026-06-12` model as the first **offline** two-view execution-profile fixture, limited to a Shot with **no required audio control** and no more than five verified references. This choice has the strongest directly readable current API-to-backend shape evidence of the inspected candidates. Derive a real versioned M4 capability descriptor/profile for its actual M7 route; map selected capability ID separately from backend model ID; capture front/reverse media bytes in fixed order; include provider-payload digest and route in the host request; and test changed source bytes, order, prompt image-number binding, unsupported audio/identity control, over-limit reference rejection, and active-task snapshot conflict before any provider submit. If the source or prompt contract cannot represent a required semantic, fail admission. Kling remains a local-backend comparison until its model/endpoint/schema compatibility is independently established. Neither fixture is authorization for a paid/production route.

## Proposed first execution-profile boundary

The first profile is a **draft fixture contract**: a selected M4 capability ID and descriptor version map to `provider_id=dashscope`, `provider_model_id=backend_model_id=wan2.7-r2v-2026-06-12`, `endpoint_id=video-synthesis`, `adapter_version=host-video-v1` and capability profile `dashscope-video-synthesis@host-video-v1`. The M4 capability ID remains a separate identity. The official API lists this dated model alongside the `wan2.7-r2v` alias; the dated ID avoids relying on an unqualified moving alias for this fixture. An offline backend probe resolved the same five-reference, always-on-audio capability and M7 submit route for both IDs. This is still no proof of regional availability or immutable vendor behavior. The input has exactly two ordered frame receipts for one admitted location pair; the prompt formatter must bind front to `Image 1` and reverse to `Image 2`, matching the official API's media ordering rule. The fixture uses a five-second output, an explicitly chosen 720P resolution, no first/end frame, no seed, and no required audio control. These values are inputs to validate, not defaults inferred from mutable backend settings.

The profile refuses a Shot requiring `silent`, `narration`, `dialogue`, unsupported identity lock, extra media, non-integer duration or a prompt beyond the selected route's limit until each has an exact mapping. In particular, the repo's `ALWAYS_ON` audio declaration cannot satisfy `silent`, while generated audio cannot establish exact narration text. Admission must check these before queueing; the backend's over-limit truncation must never be reached by this route. The draft still lacks an implemented M4 descriptor, deterministic semantic-to-prompt formatter, immutable execution projection, and same-fixture prompt test. Those are the next consumer design/implementation proof, followed by route-to-M7 planning under currentness and independent review.

A direct M4 probe instantiated a proposed `dashscope`/Wan capability descriptor and compiled a `PromptPlan` with a `location` reference and no required controls. These probes used hand-built fixture contracts, not a Take-derived admitted Shot. ## Spatial prompt projection boundary

Source inspection at `549125a6` found that `PromptPlanner.build` accepts only a Shot, method decision and resolved visual identity. It copies `shot.framing` into `composition_intent`; neither that method nor `PromptPlan` has a typed spatial-set or binding-snapshot field (`r2/production_intelligence/prompting.py:42-73`, `r2/contracts/execution.py:48-74`). `DefaultPromptCompiler` then copies generic semantic fields into a provider-neutral JSON payload (`r2/production_intelligence/prompting.py:135-167`). This explains why the admitted Take probe proves an available Shot and audio boundary but cannot prove any spatial effect. The repository graph search returned no matching R2 symbols and coverage marked the planner and advanced-creative contract as missing freshness, so these observations come from the exact design-worktree source.

The proposed first formatter input is an **exact resolved binding snapshot**, its two ordered `MASTER`/`REVERSE` frame receipts, and only the selected `VISIBLE` typed constraints from its immutable spatial set. It should emit a versioned semantic projection containing the Shot's existing subject, composition, camera and timing; a deterministic `Image 1` front / `Image 2` reverse role map; and one stable clause per supported `PRESERVE_ON_WALL` or `SHARED_SIDE_ANCHOR` constraint. Clauses must carry subject, relation and server-stamped wall without promoting `INFERRED`/`GAP` warnings to scene facts. The Wan-specific formatter may then render that projection into the exact prompt syntax of the selected execution profile. Source spans and assertion IDs stay in the captured provenance and digest even if the provider prompt omits coordinates. This is a design candidate, not current behavior.

The same-fixture acceptance case should compare the admitted Shot with and without one eligible constraint: semantic projection, provider prompt, compiled request and host request digests must change while the two image bytes and their order remain fixed. A separate reversal case must change image order, role mapping and payload digest together; swapping bytes without the prompt roles must fail admission. An `INFERRED`/`GAP`-only change may alter evidence/snapshot digest but must not add a positive spatial clause. Unsupported relation, ambiguous wall, missing object-level source span or absent pair admission fails before task creation. These tests require the still-unimplemented typed resolver and execution projection; a prose-only assertion in today's generic `PromptPlan` would not establish the authority chain.

## M4 descriptor registration boundary

`CapabilityDescriptor` has no backend model or M7 endpoint field; it records `capability_id`, `adapter_id`, `provider_id`, execution type, features, limits, source and version (`r2/contracts/capabilities.py:25-39`). The source search over `r2/**/*.py` found descriptor construction only in `r2/production_intelligence/fixture_loader.py:179-190`, where the Golden fixture uses synthetic adapter IDs and `local`/`cloud` providers. `CapabilityRegistry` accepts a supplied sequence of descriptors and observations; it does not itself load a live catalog (`r2/production_intelligence/capability_registry.py:175-196`). The inspected host route inventory separately contains `dashscope-video-synthesis@host-video-v1` (`r2/host_hardening/route_inventory.py:50`). These scoped findings mean the hand-built Wan M4 descriptor from the earlier probe is not a registered production capability.

The first implementation fixture must therefore explicitly create a versioned M4 descriptor with `VIDEO_OUTPUT` and a matching observation, plus a separate reviewed execution-profile record mapping its exact capability ID and descriptor version to the host route/model/endpoint. A stale or unknown observation must remain ineligible under the M4 matcher; route presence alone does not supply availability, credential, health or quota evidence. The fixture must prove that changing either descriptor version or host profile version rejects before queue admission. This registration and mapping are still proposed; no live catalog or activation was added.

## M4 eligibility and identity characterization

Two offline calls at design HEAD `7a3054ee` narrowed what the first profile must prove. First, a `GENERATED_VIDEO` descriptor with `VIDEO_OUTPUT` but **empty `input_modalities`** was still eligible for a fresh `VIDEO_OUTPUT`/API requirement when a synthetic observation reported credentials, endpoint and dependencies ready. This follows the current matcher: it checks hard feature strings, method, execution type and dynamic observations, but does not evaluate `input_modalities` (`r2/production_intelligence/capability_registry.py:117-171,200-303`). The synthetic observation establishes only current matcher behavior, not live route availability. Therefore the R2 two-frame route must independently require exact reference-image modality/count and reject a descriptor/profile that cannot prove them; `VIDEO_OUTPUT` eligibility alone is insufficient.

Second, two real `PromptPlan` objects differing only in `positive_prompt` produced the **same `ExecutionDecision.id` and `request_semantics_hash`**, while `DefaultPromptCompiler` produced different payloads. The direct probe reused the existing `ExecutionDecisionService` test fixtures and no provider was called. `_request_semantics_hash` currently omits `positive_prompt` (`r2/production_intelligence/execution.py:110-137`), although the compiler emits it in payload `positive` (`r2/production_intelligence/prompting.py:144-167`). The R2 spatial projection cannot rely on the decision ID/hash to detect a changed spatial clause. It must bind the full normalized prompt-plan/compiled-request digest through task evidence and the M7 host request; a same-fixture mutation of only one visible spatial clause must change those digests and fail replay under the earlier snapshot. The different compiled payload means this is an identity gap at the M4 decision layer, not proof that the eventual M7 full-request digest would collide.

## Provider-side prompt rewrite and output parameters

The currently published [Wan2.7-R2V API reference](https://help.aliyun.com/zh/model-studio/wan-video-to-video-api-reference) says `prompt_extend` defaults to `true`, which lets the service rewrite the submitted prompt. The local DashScope `_build_payload` sends `resolution`, `duration`, `watermark`, optional `ratio` and seed, but never sends `prompt_extend` (`lib/video_backends/dashscope.py:518-548`). Thus the current offline payload fixture proves exact input bytes and image order only; it does not prove the provider will consume the spatial wording unchanged. The first R2 execution profile should explicitly pin `prompt_extend=false` in the **captured provider payload** and fail if the backend cannot emit and retain it. This needs a reviewed R2-specific backend arm or typed request field; simply assuming the provider default is unsuitable for the exact-prompt fixture.

The same official reference permits five-second image-only output and `720P`, and defines reference image bounds: PNG/JPEG/BMP/WEBP without transparency, each 240–8000 pixels per side, ratio 1:8–8:1, at most 20 MB. The local test frames are 320×320 RGB PNGs, so they meet those specific format/dimension/ratio constraints, but no route admission checks those conditions yet. The profile must pin ratio explicitly (the live `VideoGenerationRequest` default is `9:16`), resolution, duration, watermark, seed policy and prompt-rewrite flag, and validate each captured frame's decoded properties before queueing. It also rejects prompt/negative-prompt overlength rather than relying on the API's documented truncation. These checks establish request admissibility, not provider spatial fidelity or a paid route decision.
