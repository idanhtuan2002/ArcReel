# M8-C two-view source custody comparison

Status: research and proposed first-source choice, not implementation acceptance. Source checkout: `design/r2-m8c-binding-authority` at `0568086f`; donor pin remains `b299bfd9f6fc3e4a1eacc580cc03d5868c2e6e83`.

## Current source facts

- M8 §8 requires source media digests and visible object spans, but does not prescribe that the two model input images are themselves approved M7 master rows (`docs/superpowers/specs/2026-09-13-r2-m8-canvas-learning-multiformat-design.md:646-657`).
- The live Gate C approval route stages a host candidate, checks it, calls the M7 `master_authority_unit(...).promote_staged` and projects the file manifest (`server/routers/gates.py:370-465`). The projection scanner selects episode-video masters only (`server/services/master_authority.py:151-167`). The existing integration fixture promotes video files with `episode_video` keys (`tests/integration/r2/host_hardening/test_master_authority_unit.py:29-86`). Those source paths prove a video-master route; they do not prove a live image-master approval route.
- The M7 candidate store is media-generic and records an immutable object reference, byte size, content digest and media-probe digest (`lib/candidate_store.py:1-25,115-174`; `r2/contracts/host_hardening.py:273-292`). `stream_probe_digest` checks ffprobe streams but does not itself prove human approval or a source image's relation to a master (`r2/host_hardening/master_authority.py:41-61`). A standalone candidate object is therefore insufficient as an approved spatial source.
- M8-A artifact-slot promotion uses the M7 generic head for non-manifest keys, but its accepted integration fixture registers and promotes video, not a two-image source pair (`tests/integration/r2/advanced_creative/test_promotion_atomicity.py:35-121`; `server/services/advanced_creative.py:55-113`).
- A bounded local probe with FFmpeg `8.0.1-3ubuntu2+esm4` decoded one synthetic 64×36 video into a PNG; ffprobe returned a PNG video stream. The parent file SHA-256 was `25d464e6ca00f8c3ce9b90313581d07b7f1b9bf3dad8606f557efbbc372be7d1`; the derived PNG SHA-256 was `3440aa8b4f244ff00e00606fc09e09a2779951789f96a722e95528a9d46b5722`. This proves only local decode feasibility, not deterministic cross-runtime output, approval, database registration or M8 acceptance.

## Options and proposed selection

| Path | Reuse and gap | Decision |
| --- | --- | --- |
| Two newly approved image masters | Can reuse M7 generic storage, but needs an image-specific approval/QA route and custody proof. Neither is evidenced by the existing Gate C video route. | Defer until that authority is designed and accepted. |
| Two exact frames derived from approved video masters | Reuses the live video approval/head path and generic immutable candidate storage. Needs deterministic frame extraction, immutable derived-frame registration and parent lineage. | Select for the first M8-C vertical slice, pending a real two-video-master fixture and independent review. |
| Two arbitrary file paths or mutable URLs | Has no exact approval/currentness or immutable content proof. | Reject. |

The selected path uses two distinct project-scoped approved M7 video master heads as potential `MASTER` and `REVERSE` parents. For each, a server-owned extraction command fixes the exact master identity/digest, zero-based decoded frame index, decoder/transform version, pixel format, output encoding and frame digest. It registers the frame bytes as an immutable derived candidate object **and** a same-transaction, immutable derivation receipt under a deterministic identity bound to that parent and extraction recipe. The existing candidate-object schema alone cannot prove parent or recipe lineage. The spatial model sees the two frame bytes; `SpatialImageSpan.source_digest` names the frame digest, while the source-binding record carries the approved parent master and its derivation receipt. Promotion and live consumption recheck both parent heads, derivation receipts and frame objects. A changed parent master invalidates the frame source for a new promotion; prior candidate evidence remains immutable history. Public wire/digests contain only opaque object identities and digests, since `object_ref` is a server filesystem path.

Two independently approved videos are not automatically a spatial pair: the pinned donor assumes front and reverse views of one location from one camera point, approximately 180 degrees apart (`scene_spatial_contract.py:187-208`). A Production Preparation `SpatialPairAdmission` must bind the exact two derived frames to one target/location, reviewed view roles, camera relation and reviewer decision before any seam, direction or duplicate lock is promoted. An unsuitable or absent pair leaves the candidate as evidence only. This is an accountable human suitability decision, not a claim that two video approvals mathematically prove camera geometry.

The design must not call a derived frame an independently approved M7 image master. The media approval comes from the exact current video master; extraction and pair suitability have separate receipts. The first implementation fixture must approve two videos through the actual Gate C path, extract/register both frames and receipts, admit a suitable pair, reject an unsuitable pair, verify bytes/digests and reject stale parent, mutated frame, wrong project, unsupported frame index and decoder-version mismatch. Until that fixture exists, this is a selected design direction rather than proven custody.

## Gate C two-master follow-up — 2026-10-03

`tests/integration/server/routers/test_gates_master_authority.py::test_two_gate_c_video_masters_have_distinct_current_heads` now approves two different video shots through the live Gate C HTTP route. It verifies two distinct project-scoped database heads, corresponding manifest projections and different video content digests. Reapproving the first shot advances only its head; the second remains exact, and the database/projection consistency check passes before and after replacement. The affected integration file passed **13 tests** with an isolated SQLite test database.

This establishes that the current Gate C route can supply two independently versioned approved video parents. It does not establish immutable frame extraction/registration, parent-to-frame receipts, spatial suitability or pair admission. In particular, two Gate C approvals alone must never authorize a `MASTER`/`REVERSE` spatial pair.

The fixture videos are synthetic black frames; their container metadata differs. A local FFmpeg first-frame probe over the same `_media` helper returned `video_digest_distinct= True` and `decoded_frame_digest_equal= True`. This makes the limitation concrete: different approved master digests need not yield different visible frames, let alone suitable front/reverse views. The later pair fixture needs intentionally distinct visual content and an accountable reviewer decision; these black-frame parents only test M7 authority behavior.

The [frame custody seam follow-up](2026-10-03-r2-m8c-frame-custody-seam.md) found two reuse limits: `DatabaseMasterResolver.get_exact` accepts a missing legacy projection, and the current `prepare_candidate` file publication can overwrite a destination created after its existence precheck. The frame service must use scoped full projection verification and an atomic no-overwrite publication operation before its receipt can be accepted.

The [frame-selection follow-up](2026-10-03-r2-m8c-frame-selection.md) proposes a zero-based decoded frame index and versioned FFmpeg recipe for the initial source path. A local three-frame probe passed, but no receipt, cross-build parity or live Gate C extraction fixture exists yet.
