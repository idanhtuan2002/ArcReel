# M8-C compiled-to-runtime submit projection

Status: source-backed design correction at `2863ff215713b07b94552106f9804122200150fb`, with one focused preplanned-attempt integration probe. No R2 route, projection, transaction-bound admission or provider submit has been implemented or tested here.

## Current runtime seam

`DefaultPromptCompiler.compile` returns a `ProviderRequest` whose payload is the semantic M4 shape: `instruction`, `subject`, `environment`, `action`, `composition`, `camera`, `timing`, `positive`, `negative`, `references`, `identity` and `controls`; its origin is `method_decision_ref` (`r2/production_intelligence/prompting.py:132-174`). The live video-backend M7 adapter independently builds a host-origin `ProviderRequest` with `_semantic_video_payload(VideoGenerationRequest)`: `prompt`, aspect ratio, duration, resolution, generation flags, seed and media digests (`lib/video_backends/execution_adapter.py:61-106,136-187`). It derives the route from the chosen backend and calls `AttemptSubmitter.submit`. These are different payload contracts. Changing only the origin field of the M4 object cannot give the M7 attempt a digest of what the current backend path actually submits.

The M4 endpoint is also a compiler profile string, `f"{adapter_id}/generate/{execution_type}"` (`r2/production_intelligence/prompting.py:104-113`), while M7's exact endpoint comes from the backend submit route inventory (`r2/host_hardening/route_inventory.py:45-105`). The projection must select and validate one registered backend route; copying M4 provider/model/endpoint/adapter version into the host request would not establish route equality.

The inspected M4 Golden fixture creates synthetic descriptors with `adapter:...` IDs, `local`/`cloud` providers and `LOCAL`/`API` execution types (`r2/production_intelligence/fixture_loader.py:179-190`). These fixtures prove M4 planner/compiler behavior, not a production mapping to any registered M7 backend. The first R2 consumer route must bind a real descriptor, model and capability profile to one frozen M7 submit tuple and show that the chosen backend actually accepts the projected control/reference/media surface. Treat any unknown mapping as incompatible before queueing; do not infer it from the Golden fixture.

`ExecutionDecisionService` currently writes the selected **capability ID** into `ExecutionDecision.model_or_tool_id` (`r2/production_intelligence/execution.py:90-101`); `DefaultPromptCompiler` copies that value to the semantic request's `model` (`r2/production_intelligence/prompting.py:165-176`). M7 `ProviderRouteSnapshot` instead requires both provider and backend model IDs (`r2/contracts/host_hardening.py:121-131`). The first real profile therefore needs an explicit versioned `(capability_id, descriptor_version) → (provider_id, backend_model_id, provider_model_id, endpoint_id, capability_profile_ref)` mapping, checked against the selected decision and route inventory. Equality of capability ID and backend model name must not be assumed. The existing M4 `execute_admitted` validates only the semantic request against `ExecutionDecision`, so it cannot prove this M7 mapping (`r2/production_intelligence/host_integration.py:59-74`).

A direct Golden fixture probe printed `SH06/SH07/SH12` as `cloud`, `adapter:sh06/07/12`, `GENERATED_VIDEO`, with `audio_intent=narration` for each. Those values illustrate why no real backend tuple can be inferred from Golden's generated-video cases. The first execution profile also needs an explicit policy for semantic controls: `narration` is not equivalent to the backend's `generate_audio` Boolean. A profile that cannot represent a required control, identity reference or timing option must reject the shot before queue admission. A deterministic prompt formatter is only one part of that proof; it must preserve all material M4 fields and show a same-fixture spatial prompt effect without silently discarding controls.

The [first-route comparison](2026-10-03-r2-m8c-first-video-route-comparison.md) now narrows the first **offline fixture** to Wan `wan2.7-r2v` for a two-view Shot with no required audio control. Its official API page directly supports the backend's ordered reference-image and Base64 data URI shape. The previous Kling local-fixture choice was withdrawn after the indexed official Omni page showed a different endpoint/schema and its current compatibility could not be confirmed. This is a fixture direction, not provider activation: visual fidelity, the real M4 profile, and the route-to-submit integration gate remain open.

The later fixture revision selects the documented dated model ID `wan2.7-r2v-2026-06-12` for the exact first profile, while retaining the same Wan2.7-R2V family comparison. The local backend resolves the same capability surface and M7 route for the alias and dated ID; regional availability and provider behavior remain unverified.

`AttemptSubmitter.submit` hashes the full host `ProviderRequest` JSON, validates task/route identity and then calls `ExecutionAttemptServiceImpl.plan_and_submit` (`r2/host_hardening/host_submit.py:70-122,164-176`). That service commits `repository.plan` before acquiring a submit fence (`r2/host_hardening/execution.py:120-154`). The current adapter does not accept a prebuilt request or an already planned attempt. `VideoGenerationRequest` is mutable and holds filesystem paths, so its media bytes can also change after a prior digest unless the R2 worker pins and rechecks them.

There is a second byte boundary inside the backend. Kling `generate` calls `_build_payload` before `submit_video_attempt` (`lib/video_backends/kling.py:446-451`), and `_build_payload` reads/encodes frame paths into a provider payload (`:358-411`). `submit_video_attempt` then hashes the path bytes again for the separate M7 semantic host request (`lib/video_backends/execution_adapter.py:76-101,166-184`), while the Kling submit callback sends the earlier provider payload (`lib/kling_backend_base.py:127-136`). An offline probe wrote `old-frame` to a local image path, built Kling's `image2video` payload, replaced the file with `new-frame`, then built the M7 semantic payload. It returned `endpoint=image2video`, `wire_has_old_bytes=True`, `host_digest_differs_from_wire_source=True`. Thus an R2 pre-submit path rehash alone cannot prove that the bytes in the provider payload match its host request. The probe made no network call and does not establish a production race frequency.

The queue is another required integration point. `TaskSpec.from_request` currently applies prompt validation for the known video task type, and `execute_generation_task` dispatches through `_TASK_EXECUTORS`; neither knows `r2_shot_generation_v1` (`lib/generation_queue_client.py:322-373,415-505`; `server/services/generation_tasks.py:3566-3629`). `GenerationQueue.enqueue_task` has a resource-based active-task dedupe guard that compares narration/text request facts only (`lib/generation_queue.py:403-486`). `TaskRepository.enqueue` may return an existing active task for a new command and still record that command's receipt against the existing task (`lib/db/repositories/task_repo.py:217-228,259-327`). Therefore command-key replay protection alone does not prevent two different spatial snapshots for one resource from aliasing one task. A new R2 arm needs a typed exact-snapshot dedupe guard.

An offline SQLite characterization made this concrete: it enqueued `r2_shot_generation_v1` twice for the same Shot/resource, with different command IDs/digests and different `binding_snapshot_digest` values. The second result had `deduped=True` and the first task ID; its durable command receipt also pointed to the first task. The temporary one-test probe passed and its test file was removed after recording the result. This is current behavior for an unimplemented R2 task type, not an accepted behavior contract or a test of a future R2 guard. The guarded R2 route must reject an active task with any different immutable snapshot/request fingerprint before recording the second receipt; exact same-fingerprint aliasing still requires a defined idempotency policy and task-evidence check.

The normal SDK `TaskSpec.from_request` also treats an unknown task type as an asset prompt and rejects a missing/non-string prompt (`lib/generation_queue_client.py:322-380,450-505`); supplying a synthetic prompt merely to pass validation would create an unchecked alternate source of generation text. The worker `_TASK_EXECUTORS` map lacks the R2 type and rejects it before execution (`server/services/generation_tasks.py:3562-3602`). The R2 route therefore needs a typed promptless task spec that accepts only immutable evidence references and expected identities, a provider-claim projection tied to the versioned execution profile, an explicit worker executor, and completion/recovery handling. The worker must derive prompt bytes exclusively from the verified task evidence. The generic queue's ability to store an arbitrary type is not evidence that the application can execute it.

Direct offline calls confirmed both boundaries: `TaskSpec.from_request(... task_type="r2_shot_generation_v1", prompt=None)` raised `TaskSpecValidationError` with `prompt_must_be_string_or_object`; `execute_generation_task` for that task type raised `ValueError("unsupported task_type: r2_shot_generation_v1")`. No worker or provider call occurred.

## Corrected design direction

1. A versioned, fail-closed R2 video execution projection consumes the exact compiled M4 request, target/binding snapshot and selected backend capability. It deterministically produces a `VideoGenerationRequest` (or an immutable equivalent) and stores both the M4 compiled-request digest and a separate projection digest. Every required semantic, reference and generation option must map or fail; a generic prompt fallback is prohibited. The projection declares the exact backend/route it supports.
2. The M7 host request must be built from the **same projected runtime request and captured media bytes** that produce the provider payload, with `host_task_ref=task_id`. For the first supported backend route, admission calculates a provider-payload digest from pinned immutable inputs and stores it in task evidence; claim rebuilds the payload from the same verified inputs, compares that digest, and retains the resulting bytes in memory for submission after the M7 fence. The exact endpoint is also bound. Its `execution_options` must include a versioned R2 identity envelope binding the compiled-request, projection, binding-snapshot, task and provider-payload digests. `AttemptSubmitter` hashes those fields as part of the complete request JSON; the backend's typed R2 arm must refuse a rebuilt or mismatched payload. The task evidence stores the full normalized projection and its digest, while public responses expose only opaque IDs/digests. Backend wire forms with nondeterministic fields require an explicit canonicalization and equivalence proof before being admitted.
3. After locking and revalidating all current authorities, the R2 worker stages `PLANNED` through the M7 repository in the same PostgreSQL transaction. It commits once, then calls the existing `AttemptSubmitter.submit` with the exact task, route and host request. Its replay check and repository plan reject a changed request or route before the provider callback; its existing lease/fence path owns submit. The transaction-bound planner must construct the same attempt identity as `AttemptSubmitter` (including capability-dependent client token and creation time), through a reviewed shared/public factory or equivalent exact contract. No database lock spans the provider call. Filesystem media inputs are rehashed immediately before submit, and a mismatch prevents the network call.
4. Queue admission adds `r2_shot_generation_v1` to validation, provider-claim projection, worker dispatch, recovery and completion paths. Both command replay and active-resource dedupe compare the full immutable R2 request/snapshot fingerprint before writing a new command receipt; a different fingerprint is a conflict, not a reused task. The existing synchronous dedupe callback receives only payload and task ID, so an R2 branch must also verify that the stored fingerprint corresponds to exact immutable task evidence rather than trusting a mutable payload field alone. The worker refuses a missing/corrupt task evidence record and never rereads a mutable disk script to rebuild its prompt.

## Focused reuse probe and remaining proof

`tests/integration/r2/host_hardening/test_preplanned_submit.py` commits a real repository `PLANNED` row, then invokes `AttemptSubmitter.submit` in a new session. A changed host request raises `AttemptIdentityMismatch` with zero provider callback calls; the exact request submits once, and exact replay does not call the provider again. The isolated SQLite fixture passed **1 test**. This proves the existing submitter can continue this exact externally planned attempt; it does not exercise R2 admission, a PostgreSQL transaction/lock, the backend adapter, crash recovery or an actual provider.

Required integration proof traces route → stored task evidence → claim → same-transaction currentness plus `PLANNED` attempt → exact `AttemptSubmitter.submit` → provider boundary. Cases include stale head before plan (zero attempt/network calls), head advance after plan (pinned attempt), changed command body, active task with another snapshot, changed runtime media both before and after provider-payload capture, route mismatch, crash after plan, and provider failure/unknown outcome. The focused probe satisfies only the existing-submit-reuse slice of this gate.
