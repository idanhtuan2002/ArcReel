## A3 target evidence already present

`ProfilePublicationAuthorizationLease` is a typed contract, not a runtime
admission implementation. It fixes `PROFILE_PUBLICATION`, scope/actor/command,
request and subject digests, policy and evidence bindings, and enforces an
issued-to-admission window of at most 30 seconds
([`r2/contracts/quality.py:738`](../../r2/contracts/quality.py#L738),
[`r2/contracts/quality.py:753`](../../r2/contracts/quality.py#L753)).
`ProfilePublicationSubject` binds the draft scope/creator, incremented
revision, parent revision, and expected profile revision
([`r2/contracts/quality.py:815`](../../r2/contracts/quality.py#L815)); the
request requires `PUBLISH_PROFILE`
([`r2/contracts/quality.py:836`](../../r2/contracts/quality.py#L836)).

The accepted A1 digest code currently registers the subject and request digest
domains and normalizes a request digest to command scope plus subject; it does
not register a lease domain or admit a lease
([`r2/quality/digests.py:18`](../../r2/quality/digests.py#L18),
[`r2/quality/digests.py:75`](../../r2/quality/digests.py#L75),
[`r2/quality/digests.py:103`](../../r2/quality/digests.py#L103)). This is a
concrete runtime gap, not evidence that a generic receipt or grant is enough.

The rebase describes the desired properties as proposed A work: separate
profile CAS head, receipt-first replay and second lookup under a command guard,
and a profile publication writer that does not acquire master rows
([`docs/superpowers/specs/2026-10-25-r2-m10-v2-rebase.md:98`](../superpowers/specs/2026-10-25-r2-m10-v2-rebase.md#L98),

## Candidate A: `ExplorationRepository.append_revision`

`ExplorationRepository.append_revision` supplies a real repository-level
mechanics pattern. Its caller provides an `AsyncSession`; the method itself
flushes but does not commit. It computes a command digest, reads a replay,
locks the command key, reads the replay again, validates the payload digest,
inserts/locks a candidate head, conditionally advances its version, inserts an
immutable revision, flushes, and stages a receipt
([`lib/db/repositories/advanced_creative.py:232`](../../lib/db/repositories/advanced_creative.py#L232)-[`lib/db/repositories/advanced_creative.py:322`](../../lib/db/repositories/advanced_creative.py#L322)).

For non-genesis revisions it reads the head with `FOR UPDATE`, checks parent,
revision and expected version, then uses a version-qualified update whose
`rowcount` must be one
([`lib/db/repositories/advanced_creative.py:267`](../../lib/db/repositories/advanced_creative.py#L267)-[`lib/db/repositories/advanced_creative.py:289`](../../lib/db/repositories/advanced_creative.py#L289)). Replay compares both command and result digests
([`lib/db/repositories/advanced_creative.py:324`](../../lib/db/repositories/advanced_creative.py#L324)-[`lib/db/repositories/advanced_creative.py:337`](../../lib/db/repositories/advanced_creative.py#L337)).

Existing fixture pointers exercise these mechanics, not an M10 profile:

- `tests/integration/lib/db/repositories/test_advanced_creative.py:96-157` covers exact replay, conflict, stale parent/head, immutable history, and digest mismatch.
- `tests/integration/lib/db/repositories/test_advanced_creative.py:198-234` covers rollback leaving no revision/receipt and PostgreSQL-gated competing genesis/head appends.

**Reuse gap:** this repository persists M8 `ExplorationRevision` and
`M8CandidateHeadModel` under operation `APPEND_REVISION`, with candidate
payload/lineage semantics and its own receipt namespace. It neither accepts an
M10 publication subject/request/lease nor demonstrates the A3 profile-head
schema, outbox payload, lease admission time, or transaction composition.
Reuse, if later selected, is limited to mechanically requalifying the pattern
against M10-owned rows and receipts; no direct reuse is qualified by this note.

## Candidate B: current Showrunner-grant readers

`CurrentShowrunnerGrantReader.require_current_locked` requires a transaction,
locks a grant head, verifies the current event, obtains database time, and only
returns an active `ISSUE` event
([`server/services/governance_grants.py:238`](../../server/services/governance_grants.py#L238)-[`server/services/governance_grants.py:259`](../../server/services/governance_grants.py#L259)). Its docstring expressly says activation needs external custody. `CheckpointedShowrunnerGrantReader` additionally loads and verifies a signed checkpoint and compares that checkpoint's scoped sequence/digest against the locked current event
([`server/services/governance_grants.py:310`](../../server/services/governance_grants.py#L310)-[`server/services/governance_grants.py:350`](../../server/services/governance_grants.py#L350)).

Concrete fixtures are `tests/integration/r2/governance/test_checkpointed_grant_reader.py:45-87` (matching/missing/mismatched/old head and loader failures) and `:90-175` (PostgreSQL-gated reader/importer serialization). Those fixtures belong to the grant-chain/checkpoint scope.

**Reuse gap:** these readers consume a signed Showrunner grant scoped by
`GrantScopeV1`; they do not validate the M10 profile-publication action,
request/subject/policy/evidence digest bindings, A3 30-second lease, or create
an M10 receipt/outbox. They are not evidence that the caller is a qualified
M10 Human publication custodian, and no authority composition is selected here.

## Donor status and follow-up qualification

The earlier audit pins OpenMontage
`08e2151fa02de28a5d6a312b3d575692bf147ad7` and Kalinga
`e4b5a2173ca03d365aad565a89fcc43159b44f9b`, but characterizes their relevant

([donor audit:109-111](2026-10-23-r2-m10-research-decision-donor-audit.md#L109)). They are not qualified A3 donors by this inventory.

Before an implementation or authority decision, the owner needs to qualify:

1. M10-owned models/migration and exact session/transaction boundary for profile revision, CAS head, receipt, and outbox together.
2. The exact command-guard and receipt identity/payload behavior under retries and concurrent writers, with PostgreSQL interleaving evidence at the intended schema.
3. Who issues/admits a `ProfilePublicationAuthorizationLease`, how its action,
   scope, request/subject/policy/evidence bindings are checked under the same
   transaction, and whether database time semantics satisfy final 30-second
   admission.
4. Recovery/outbox dispatch semantics and failure fixtures; no existing cited
   source establishes them for M10.

### Main-verified primary-reference note

The parent independently verified exact installed-package evidence at
`r2-v2-main/.venv/lib/python3.13/site-packages/sqlalchemy/ext/asyncio/session.py`:
SQLAlchemy 2.0.52, SHA-256
`875e89b14110e7b9bd435c86bf26716a1e38031638e80179bc044f1292c43e7e`,
states at lines 210-211 that `AsyncSession` is unsafe across concurrent tasks.
The same rule appears in the later series documentation
([SQLAlchemy 2.0 asyncio docs](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html)). PostgreSQL 18 documents that
`CURRENT_TIMESTAMP`/`transaction_timestamp()` are transaction-start values,
whereas `clock_timestamp()` is actual current time
([PostgreSQL 18 datetime functions](https://www.postgresql.org/docs/18/functions-datetime.html)).
The worktree pins SQLAlchemy 2.0.52, Alembic 1.19.1 and asyncpg 0.31.0 in
`uv.lock`; the installed SQLAlchemy fact is exact-version evidence, while the
published documentation remains series-level context.
`deploy/production/docker-compose.yml:3` declares the floating image tag
`postgres:18-alpine`; the local `psql` is 18.6 client-only. Neither fact proves
the live server version or image digest, and this inventory chooses no clock
expression.
