# M8-C route-to-M7 submit boundary

Status: source-grounded design research, updated with a focused integration probe; no R2 bridge implementation. Inspected from `design/r2-m8c-binding-authority` after `78662879`. The original origin-only proposal is superseded by the [runtime-projection correction](2026-10-03-r2-m8c-runtime-submit-projection.md): the M4 compiled payload and live video-backend M7 payload have different shapes.

## Observed contracts

- `DefaultPromptCompiler.compile` creates `ProviderRequest` with `method_decision_ref=decision.method_decision_ref`, `prompt_plan_ref=plan.id`, and no `host_task_ref` (`r2/production_intelligence/prompting.py:132-174`). `ProviderRequest.require_exactly_one_origin` requires exactly one of method decision and host task (`r2/contracts/execution.py:103-121`). A host queue submit cannot simply add `host_task_ref` to that compiled object.
- `AttemptSubmitter._validate_request` requires `request.host_task_ref == task_id`, exact route provider/model/adapter/endpoint (`r2/host_hardening/host_submit.py:165-175`). It hashes the complete `ProviderRequest` JSON as the M7 attempt request digest and uses task attempt number 1 (`r2/host_hardening/host_submit.py:78-97,147-162`). That digest covers a snapshot field only if a reviewed R2 bridge actually places it in the provider request or an equally exact M7 attempt identity.
- `ExecutionAttemptServiceImpl.plan_and_submit` calls `repository.plan`, commits, then acquires an attempt fence and commits before `adapter.submit` (`r2/host_hardening/execution.py:118-154`). Any authority-currentness check in a separate transaction before this plan is vulnerable to a head change before the attempt is recorded. The intended linearization point must include both the currentness proof and the durable `PLANNED` attempt in one transaction.
- Existing `build_attempt_submitter` composes one repository/service on the supplied session (`server/services/execution_attempts.py:119-145`). A later [focused integration probe](2026-10-03-r2-m8c-runtime-submit-projection.md) confirmed `AttemptSubmitter.submit` can continue a separately committed, exact `PLANNED` row through its existing replay/lease/fence path. The missing seam is a reviewed way to construct the same planned-attempt identity during the currentness transaction, not a new resume operation.

## Required R2 bridge

1. A versioned R2 execution projection takes the exact compiled M4 request and immutable queued R2 task, then maps every required semantic field into one backend runtime video request or fails closed. The typed R2 backend arm derives the host-origin `ProviderRequest` from that same runtime request and media bytes, binding the original method-decision ID, compiled/projection digests and binding snapshot in versioned `execution_options`. A test must show the derived request matches the backend submission path, passes `ProviderRequest` validation and `AttemptSubmitter._validate_request`, and rejects a mismatched task, route, media input or compiled semantic.
2. A transaction-bound `admit_and_plan_spatial_attempt` operation locks and rehashes target/admission, binding, pair, parent masters, frame derivations and candidate objects, recomputes the exact bridge request digest, and calls the M7 attempt repository's plan operation under the same PostgreSQL session before one commit. Its command/attempt identity binds `(task_id, attempt_no=1, route, request_digest, binding_snapshot_digest)`. Failure or a stale head creates no `PLANNED` attempt; exact replay returns the same one.
3. After that commit, existing `AttemptSubmitter.submit` replays the already planned exact attempt through its lease/fence/submit path. It refuses a different request or route; the snapshot digest is covered when placed in the exact host request. The preplanner must share its attempt-identity construction contract with the submitter. A new head committed after the admission transaction does not rewrite the pinned attempt; a head committed before it blocks the plan. No database lock spans the provider call. Crash-after-plan recovery still requires its own integration proof.

The runtime projection, exact task evidence and transaction-bound planner are runtime contract changes. They need implementation and an integration test tracing route → task → currentness/plan transaction → M7 submit with stale-before-plan, changed-replay, crash-after-plan and provider-failure cases. The focused preplanned-submit probe establishes only existing M7 submitter reuse.
