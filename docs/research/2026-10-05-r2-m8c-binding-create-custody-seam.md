## Current source

- `ProductionBinding` is a v1 body with target, semantic and production refs, role and sorted `asset_refs`; it has no content digest, approval, provenance or persistent authority field (`r2/contracts/preparation.py:20-33`). The Golden A preparation flow constructs one from a caller-supplied reused asset ref in memory (`r2/m3/preparation.py:53-82`). `ProductionReadinessEvaluator.evaluate` accepts caller-supplied bindings and a caller-supplied `binding_snapshot_ref`; its `is_current` only compares the two supplied version/ref strings (`r2/production_intelligence/readiness.py:27-114`). These are reusable pure behavior, not live binding authority.
- The M1 contract spec calls the body a semantic-to-production bridge and distinguishes `semantic_ref` from `production_ref`. It permits empty `asset_refs` only for roles where `production_ref` itself is sufficient (`docs/superpowers/specs/2026-09-06-r2-m1-contract-kernel-design.md:489-518`). A live writer must therefore define and verify the production identity as well as each supplied asset; merely accepting an empty list would not close the custody gap.
- A Take-derived Shot points to a Scene, and the Scene has an optional `location_ref` copied from the admitted screenplay (`r2/contracts/production.py:15-35`, `r2/production_intelligence/take_director.py:68-79`). The first `LOCATION` create command can require that field to be present and use its exact value as `semantic_ref` after the current target/admission read. This proves the binding refers to the admitted story's named location; it does not independently prove Canon approval of that name.
- The current `AssetRepository` permits `update`, `delete` and replacement of derivatives, and its `get_by_id` returns a mutable row (`lib/db/repositories/asset_repo.py:39-95,114-136`). The prior bounded model inspection found no approval or content digest on that row (`docs/research/2026-09-30-r2-m8c-production-binding-authority.md`). A binding writer cannot treat existence of that ID as immutable approved reference custody.
- M7 `MasterHeadSnapshot` includes artifact key, version, candidate ID, object ref, content digest and approval record (`r2/contracts/host_hardening.py:285-293`). `DatabaseMasterResolver.get_exact` compares a supplied legacy projection with the database head, but it does not own the new binding transaction or verify file bytes (`r2/host_hardening/master_resolver.py:32-54`). The scoped `verify_masters` path checks current database/projection identities for selected keys (`server/services/master_authority.py:195-225`). `FrameDerivationService._parent` already verifies projection, candidate metadata and video bytes within a supplied session (`server/services/spatial_source.py:278-309`), while `SpatialFrameReader.read_locked` reuses it for a current frame receipt (`server/services/spatial_frame_reader.py:37-107`). These readers assume the caller holds the parent row lock; `serialized_artifacts` obtains it in a newly opened transaction, so binding creation still needs a reusable same-session lock operation at the agreed later M7 stage (`server/services/master_authority.py:76-103`).
- The proposed binding vector fixes canonical v1 body, envelope and snapshot bytes. Its `spatial_set_digest` and target digests are shaped placeholders, and its `asset_refs` are opaque sample strings (`tests/fixtures/r2/m8c_binding_snapshot_vectors.json`, `docs/research/2026-10-03-r2-m8c-binding-snapshot-fingerprint.md`). The pure test proves digest propagation only; it does not prove target or asset custody. The newly accepted target resolver can prove current target/admission in the caller's transaction (`r2/target_registry/resolver.py`), but does not prove the binding's reference assets.

## Options and recommendation

1. **Use the global Asset row as the binding proof:** smallest schema change, but update/delete and absence of immutable approval/content evidence leave the binding claim unverifiable. Reject for live authority.
2. **Accept opaque refs or the synthetic fixture as sufficient:** allows an early CAS table, but a client could claim unapproved or stale media and receive a valid-looking snapshot. Reject for live create/readiness.
3. **Record exact production and asset reference claims in the immutable binding envelope:** preferred first authority path. Keep the v1 `ProductionBinding` body and its existing serialization intact. For the initial two-frame `LOCATION` binding, use the already implemented frame-derivation receipts as the asset owners: set each `asset_ref` to its immutable frame candidate ID; a server-derived `production_ref` identifies the sorted two-frame source group, and `semantic_ref` comes from the current Scene's nonempty `location_ref`. The claim for each ref binds its scoped receipt ID/digest, frame candidate ID/content digest and parent M7 master identity/digest. The writer locks sorted parent M7 rows in the same transaction after admission → target → binding, then reuses `SpatialFrameReader.read_locked` to check current parent approval/projection and PNG bytes before committing. The binding envelope digest covers the sorted claims. `FrameDerivationReceiptV1` contains no view field (`r2/contracts/spatial_source.py:16-49`), so binding creation cannot label a frame as MASTER/REVERSE or assert pair suitability. That separate human decision must precede spatial promotion and live READY status. Unsupported source families fail closed. The exact group-ref syntax and claim fields must be frozen in a vector before schema work.

Option 3 preserves the existing v1 body while giving the authority reader a checkable asset meaning. It is an inference from the observed mutable Asset row, existing M7 master/frame evidence and ADR-0102's custody requirement, not an accepted implementation design. PostgreSQL's [explicit-locking guidance](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-DEADLOCKS) supports a consistent cross-object lock order, and SQLAlchemy's [AsyncSession guidance](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks) requires one mutable session to be used sequentially per task; neither proves this project's particular order.

## Next gate

Before a binding create/CAS writer, freeze one legitimate version-1 `LOCATION` binding fixture with real registered target refs and two exact frame-receipt claims, plus changed-source and forged-claim variants. Specify a same-session M7 row-lock port and reuse `SpatialFrameReader.read_locked` after that lock in admission → Scene → Shot → binding → sorted M7 master order. Then write a bounded schema/digest/read packet and a separate create/CAS packet with PostgreSQL races against target advance, master advance and same-command replay. A synthetic envelope vector, standalone binding table or pure readiness test cannot establish live authority. Pair admission, absent/rejected-pair readiness, spatial-set promotion, route-to-submit and release remain separate gates.
